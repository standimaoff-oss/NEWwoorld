# Архитектура NEWwoorld

Документ описывает, **где что живёт и почему именно так**. Требования, из
которых следует эта структура, — в [`../ТЗ.md`](../ТЗ.md).

---

## Слои

Проект разделён на четыре слоя. Правило простое: **зависимости идут только
вниз**. Слой не знает о слоях выше себя.

```
  игра          game/scenes/game/     мир, игрок, HUD
  меню          game/scenes/menu/     главное меню, настройки, титры
  каркас        game/scripts/         сервисы, системы, утилиты
  нативный      gdextension/src/      C++ (разрушение, поле ветра)
```

Каркас не знает, существует ли меню. Нативный слой не знает о каркасе — он
отдаёт данные в форме, описанной контрактом, а кто их забирает, ему
безразлично.

Нарушение направления — самый дорогой вид ошибки в этом проекте: он не
ловится компилятором и приводит к циклам autoload-инициализации, которые
проявляются как случайные `null` в рантайме.

## Autoload-сервисы

Одиннадцать одиночек, загружаемых движком до первой сцены. **Порядок в
`project.godot` значим**: сервис может обращаться в `_ready()` только к тем,
что загружены раньше него.

| # | Имя | Файл | Отвечает за |
| --- | --- | --- | --- |
| 1 | `GameConfig` | `autoload/game_config.gd` | Константы всего проекта: пути к сценам, слои физики и рендера, параметры игрока, бюджеты разрушения, имена аудиоканалов |
| 2 | `EventBus` | `autoload/event_bus.gd` | Сигналы между слоями. Единственный способ, которым каркас узнаёт об игре |
| 3 | `Diagnostics` | `autoload/diagnostics.gd` | Кольцевой журнал событий с уровнем, тегом и временем |
| 4 | `PerfMonitor` | `autoload/perf_monitor.gd` | Сбор метрик кадра: FPS, percentiles, память, draw calls |
| 5 | `SettingsService` | `autoload/settings_service.gd` | Чтение, запись, валидация и применение настроек |
| 6 | `SaveService` | `autoload/save_service.gd` | 6 слотов сохранений, регистрация провайдеров данных |
| 7 | `AudioService` | `autoload/audio_service.gd` | Воспроизведение, громкость в дБ, позиционный звук |
| 8 | `SceneService` | `autoload/scene_service.gd` | Переходы между сценами через экран загрузки |
| 9 | `QualityService` | `autoload/quality_service.gd` | Применение профилей качества к окружению и солнцу |
| 10 | `ThemeService` | `ui/theme_builder.gd` | Построение темы интерфейса |
| 11 | `DestructionService` | `systems/destruction_service.gd` | Разрушение: выбирает C++ или GDScript-бэкенд |

### Почему `GameConfig` первый

Он не зависит ни от чего и содержит константы, нужные всем остальным. Если
поставить его позже, `_ready()` любого из предыдущих сервисов получит `null`
при обращении к `GameConfig.SOMETHING` — и ошибка будет выглядеть как
«случайный краш при запуске», потому что порядок autoload в инспекторе
неочевиден.

### Autoload ≠ синглтон движка

`Engine.has_singleton("GameConfig")` вернёт `false`. Autoload — это обычный
узел в дереве по пути `/root/GameConfig`, добавленный движком. Отличие
существенно: к autoload обращаются по имени узла, а не через `Engine`, и он
существует только пока жив корень дерева сцены.

## Системы (не autoload)

| Файл | Что делает |
| --- | --- |
| `systems/object_pool.gd` | Пул переиспользуемых узлов. Обломки разрушения создаются и удаляются сотнями; без пула это сотни аллокаций на кадр |
| `systems/quality_profile.gd` | `Resource` с бюджетом профиля: разрешение теней, MSAA, дальность отрисовки, лимит обломков |
| `systems/wind_system.gd` | Узел, публикующий параметры ветра как глобальные shader-переменные |

`WindSystem` — узел в сцене, а не autoload: ветер имеет смысл только внутри
мира, и в меню он не нужен.

## Разрушение: два бэкенда

`DestructionService` умеет ломать объекты двумя способами:

- **нативный** — `NewwoorldFracturer` из C++ (быстрый, воксельная сетка);
- **запасной** — чистый GDScript (работает, если расширение не собрано).

Выбор происходит в рантайме через `ClassDB.class_exists()`. Это означает,
что **игра запускается и без собранного расширения** — медленнее, но без
падения.

Обратная сторона: если расширение собралось под именем, которого нет в
`.gdextension`, движок его молча не загрузит, игра переключится на запасной
путь, и никто не увидит ошибки. Единственная защита — сверка имён файлов в
CI (задание `build-extension`) и проверка формы возвращаемых данных
(`tools/verify/check_backend_contract.py`).

Именно расхождение формы данных уже случалось: C++-бэкенд возвращал куски с
ключом `voxel`, GDScript — без него. Оба работали по отдельности, а тест,
сравнивающий их, падал случайным образом в зависимости от того, какой бэкенд
загрузился. Теперь ключи перечислены в `DestructionService.PIECE_KEYS` и
сверяются статически.

## Настройки

Схема настроек отделена от сервиса:

- `settings/settings_schema.gd` — **39 ключей**, их типы, диапазоны,
  значения по умолчанию и разбивка по разделам. Чистые данные.
- `autoload/settings_service.gd` — чтение, запись, валидация, применение.

Разделение вынужденное, а не эстетическое: в одном файле получалось 876
строк при лимите 700 (`gdlint max-file-lines`). Но даже без линтера оно
правильное — форма настроек строит интерфейс по схеме, и ей не нужен сервис.

Форма (`ui/settings_form.gd`) создаёт виджеты по типу ключа: `BOOL` →
`CheckBox`, `FLOAT`/`INT` → `HSlider`, `ENUM` → `OptionButton`. Добавление
ключа в схему автоматически добавляет строку в интерфейс — править `.tscn`
не нужно.

## Меню

Главное меню — **не `Control`**, а `Node`. Причина: сцена, укоренённая в
`Control`, ненадёжно отображает 3D-фон (дерево `Viewport` строится иначе, и
3D-узел внутри `Control` оказывается вне ожидаемого порядка отрисовки).
Внутри `Node` живут `Node3D`-фон и `CanvasLayer` с интерфейсом.

Фон меню — процедурное небо (`shaders/menu_backdrop_sky.gdshader`, ~2 КБ),
а не HDRI-панорама (4–20 МБ). Бюджет закреплён в сцене и проверяется тестом
`test_menu_backdrop_budget.gd`: ≤512 узлов, ≤500 000 треугольников, ≤2
источника теней.

Титры (`scenes/menu/credits_panel.tscn`) читают `data/credits.json` и
показывают контакты: почту, сайт, репозиторий, трекер ошибок. В Godot **нет
`LinkLabel`** — кликабельная ссылка делается плоской `Button` (она же
получает фокус с клавиатуры) либо `RichTextLabel` с bbcode `[url]` и
сигналом `meta_clicked`.

## Шейдеры

| Файл | Назначение |
| --- | --- |
| `wind_foliage.gdshader` | Ветер на растительности: смещение вершин по глобальным параметрам |
| `dissolve_destruction.gdshader` | Растворение при разрушении |
| `menu_backdrop_sky.gdshader` | Процедурное небо меню |
| `post_grade.gdshader` | Цветокоррекция, включая режим для дальтоников (0–3) |
| `water_surface.gdshader` | Вода с глубиной по `-VERTEX.z` |
| `outline_select.gdshader` | Инвертированный корпус для обводки выделения |

Два факта о языке шейдеров Godot, которые легко забыть и трудно отладить:

- в `spatial`-шейдере во фрагментной стадии `VERTEX` задан **в пространстве
  вида**, поэтому линейное расстояние до камеры — это `-VERTEX.z`;
- глобальные shader-параметры объявляются обычным `uniform` и сопоставляются
  **по имени**. Ключевого слова `global` в языке нет, и отличить глобальный
  параметр от поля материала по синтаксису невозможно.

Второе означает, что опечатка в имени uniform — это не ошибка компиляции, а
молча неработающий эффект. Поэтому `tools/verify/check_backend_contract.py`
сверяет имена параметров ветра между GDScript (`WindSystem`) и шейдерами.

## Карта и точки интереса

Карта 500×500 м с деревней собирается процедурно и потоково. Модули образуют
цепочку с односторонними зависимостями — ни один из них не обращается к тому,
кто стоит ниже по списку:

| Модуль | Отвечает за | Зависит от |
| --- | --- | --- |
| `MapConfig` | размеры, бюджет узлов, прочность материалов, группы | `GameConfig` |
| `TerrainGenerator` | высоты по абсолютным мировым координатам, LOD | `MapConfig` |
| `VillageLayout` | где стоят дома, дорога, деревья; записи точек интереса | `MapConfig`, `TerrainGenerator` |
| `RoomLayout` | планировка помещений как чистые данные + прочность ролей | `MapConfig` |
| `PoiDetails` | проёмы, мебель, наружные детали, комнаты | `MapConfig`, `RoomLayout` |
| `SurfaceRules` | роль поверхности → материал и характер урона | `RoomLayout`, `MaterialLibrary` |
| `MaterialLibrary` | кэш материалов, стекло, металл, эмиссия | — |
| `InteriorBuilder` | план → дерево узлов точки интереса | все вышеперечисленные |
| `ChunkBuilder` | чанк: рельеф, дорога, постройки, растительность | `MaterialLibrary`, `InteriorBuilder`, `VillageLayout` |
| `WorldStream` | какие чанки живы, бюджет, высвобождение | `ChunkBuilder` |

**Точка сборки — `InteriorBuilder`.** Модули планировки (`RoomLayout`,
`PoiDetails`) не вызывают друг друга: `PoiDetails` дополняет план, полученный
от `RoomLayout`, но не строит его. Если соединить их напрямую, возникает цикл
`RoomLayout → PoiDetails → RoomLayout` (см. `docs/TROUBLESHOOTING.md`).

### Соглашения о данных плана

Нарушение любого из них выглядит в игре как «что-то не так», а не как ошибка,
и не ловится ни синтаксисом, ни типами:

1. **Все позиции — центры объёмов**, а не их основания. Элемент, заданный
   координатой основания, тонет в полу на половину своей высоты.
2. **Расстановка мебели считается от внутренних граней стен**
   (`half − толщина`), а не от габарита постройки. Отсчёт от габарита
   вдвигает мебель в толщу стены.
3. **Общие положения задаются константами геометрии.** Перегородка бункера
   (`BUNKER_PARTITION_X_RATIO`, `BUNKER_PARTITION_Z_RATIO`) и лестничный
   проём (`STAIR_WELL_X_RATIO`, `STAIR_WELL_WIDTH`) объявлены один раз и
   используются и стеной, и мебелью, и маршем. Две копии числа расходятся, и
   мебель оказывается в бетоне, а лестница — в потолке.
4. **Каждая панель знает свой этаж** (`"floor"`) и тип (`"interior"`).
   Пометка ставится по диапазону (`_tag_range`), а не параметром
   `_wall()`: иначе аргумент проходит через четыре уровня вложенности.

### Дерево узлов точки интереса

```
<id точки>                       Node3D, группы «streamed» и «poi»
├── floor_0                      этаж — отдельный узел, чтобы этаж
├── floor_1                      можно было обрушить целиком
│   ├── panel_N                  Destructible → MeshInstance3D «mesh»
│   │                            → StaticBody3D «body» → CollisionShape3D
│   ├── window_N                 то же, но cast_shadow = OFF
│   └── door_N                   Door (extends Interactable)
├── props                        наружные детали
├── lamps                        колбы + OmniLight3D (тени выключены)
└── roof                         имя обязательно именно такое — его
                                 проверяет интеграционный тест потока
```

`mesh_node` и `collider_node` у `Destructible` задаются **явно**: автопоиск
смотрит только детей первого уровня, а `create_trimesh_collision()` создаёт
тело внуком — без явной ссылки разрушенная стена оставила бы невидимую
преграду.

## Где искать конкретное

| Нужно | Куда |
| --- | --- |
| Добавить настройку | `settings/settings_schema.gd` — только туда |
| Добавить сцену | `game/scenes/<слой>/` + регистрация в `tools/verify/check_data.py` и в смоук-тесте |
| Добавить input action | `tools/setup/generate_project_godot.py`, затем перегенерировать |
| Добавить autoload | Тот же генератор, порядок в списке `AUTOLOADS` значим |
| Добавить слой физики | `GameConfig.PhysicsLayer` + генератор (имена слоёв в `project.godot`) |
| Добавить ассет | `docs/ASSET-PIPELINE.md` и `game/assets/ATTRIBUTION.md` |
| Добавить тест | `game/tests/<категория>/`, затем `.gutconfig.json` уже знает каталог |
| Добавить роль поверхности | `RoomLayout.SurfaceRole` (только в конец перечисления) + `ROLE_INTEGRITY` в том же файле + `ROLE_RECIPES` и `ROLE_DAMAGE_MULTIPLIER` в `SurfaceRules` |
| Добавить мебель | `PoiDetails._add_furniture()` — позиция от внутренних граней стен |
| Добавить точку интереса | `VillageLayout` (запись) → `PoiDetails` (наполнение) → `InteriorBuilder.build()` |
