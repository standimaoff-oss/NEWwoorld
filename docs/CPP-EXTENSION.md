# C++ GDExtension

Да, в Godot есть C++. Это не стороннее решение, а официальный механизм:
сам движок написан на C++, а GDExtension — поддерживаемый способ добавить
собственный C++-код **без пересборки движка**.

---

## Как это работает

Расширение компилируется в разделяемую библиотеку (`.so` / `.dll` / `.dylib`
/ `.wasm`), а текстовый файл `.gdextension` внутри проекта сообщает движку,
где её искать и какую C-функцию вызвать при загрузке.

```
gdextension/src/*.cpp  --scons-->  game/bin/libnewwoorld.linux.template_debug.x86_64.so
                                            ^
                                            | объявлено здесь
                                   game/bin/newwoorld.gdextension
```

Файл `.gdextension` обязан лежать **внутри** каталога проекта (`res://`) и
может ссылаться только на пути внутри `res://` — поэтому библиотеки кладутся
в `game/bin/`.

Альтернативы в Godot 4:

| Способ | Когда |
| --- | --- |
| GDScript | встроен, не требует сборки. Подавляющая часть игровой логики |
| **C++ (GDExtension)** | тяжёлые вычисления, существующая C++-библиотека |
| C# (.NET) | только в сборке Godot с Mono; экспорт на мобильные и web ограничен |
| Rust (`gdext`) | тот же GDExtension, но на Rust |

## Классы проекта

Оба наследуют `RefCounted` и регистрируются на уровне
`MODULE_INITIALIZATION_LEVEL_SCENE`.

### `NewwoorldFracturer`

Разламывает меш по воксельной сетке.

```cpp
Array fracture(const Mesh &mesh, const Transform3D &transform,
               const Vector3 &impact_point, const Vector3 &impact_normal,
               float energy, float cell_size, int chunk_budget);
```

Возвращает массив словарей, каждый — один обломок:

| Ключ | Тип | Смысл |
| --- | --- | --- |
| `mesh` | `ArrayMesh` | геометрия обломка |
| `offset` | `Vector3` | смещение относительно точки удара |
| `impulse` | `Vector3` | импульс для `RigidBody3D` |
| `spin` | `Vector3` | угловая скорость |
| `piece_index` | `int` | порядковый номер |
| `voxel` | `Vector3i` | ячейка сетки, из которой взят обломок |

Три решения, каждое со своей причиной:

**Обломки сортируются по расстоянию до точки удара, а бюджет отбрасывает
ДАЛЬНИЕ.** Интуитивно хочется отбросить ближние — они мельче. Но при взрыве
игрок смотрит на точку удара: потеря дальнего обломка незаметна, потеря
ближнего выглядит как «взрыв не сработал». Жёсткий потолок `kHardChunkCap =
512` не даёт одному вызову породить тысячи тел.

**Вращение детерминировано** (`_spin_hash` от индекса и координат ячейки).
Случайное вращение сделало бы повтор одного и того же взрыва визуально
разным, что ломает и воспроизводимость тестов, и ощущение контроля у игрока.

**Вершины переназначаются на каждый обломок.** Общий буфер с разными
индексами означал бы, что GPU обрабатывает вершины всех обломков, даже
невидимых. Для десятков кусков это незаметно, для сотен — разница в разы.

### `NewwoorldWindField`

Процедурное поле ветра.

```cpp
PackedVector3Array sample_batch(const PackedVector3Array &positions);
Vector3 sample(const Vector3 &position);
float turbulence_at(const Vector3 &position);
```

Целочисленный хеш-шум с трилинейной интерполяцией и фрактальное суммирование
(fBm). Намеренно без `float`-хешей и без `sin()`: результат одинаков на всех
платформах, что важно для воспроизводимости и для сетевой синхронизации, если
она появится.

`sample_batch` существует потому, что вызов через границу GDExtension стоит
дорого. Обработать 500 позиций одним вызовом заметно дешевле, чем 500
вызовами по одной.

## Контракт с GDScript

Нативный слой и GDScript обязаны возвращать данные **одинаковой формы**.
Это не формальность: `DestructionService` выбирает бэкенд в рантайме через
`ClassDB.class_exists()`, поэтому игра работает и без собранного расширения —
но если формы расходятся, поведение начинает зависеть от того, загрузилось
расширение или нет.

Такая ошибка уже случилась: C++ возвращал ключ `voxel`, GDScript — нет.
Сейчас ключи перечислены в `DestructionService.PIECE_KEYS`, а соответствие
проверяется статически:

```bash
python3 tools/verify/check_backend_contract.py --strict
```

Проверяются три оси: ключи возвращаемых словарей, арность вызова
`.call("fracture", …)` и имена параметров ветра между `WindSystem` и
шейдерами.

## Сборка

### SCons — канонический путь

```bash
cd gdextension
scons platform=linux   target=template_debug   -j8
scons platform=windows target=template_debug   -j8
scons platform=macos   arch=universal          -j8
scons platform=web     target=template_release use_hot_reload=no -j8
```

`godot-cpp` официально собирается только SCons, и его `SConstruct` сам
разруливает кросс-компиляцию, флаги ABI, точность float и таргеты.

Полезные переменные:

| Переменная | Значения |
| --- | --- |
| `platform=` | `linux`, `windows`, `macos`, `android`, `ios`, `web` |
| `target=` | `template_debug`, `template_release`, `editor` |
| `arch=` | `x86_64`, `arm64`, `universal`, `wasm32` |
| `dev_build=yes` | asserts; медленнее, но видны ошибки C++ |
| `float=64` | только для double-precision сборок Godot |
| `use_hot_reload=no` | обязательно для web |

### CMake — для IDE

```bash
cmake -S gdextension -B build-cmake -DGODOTCPP_TARGET=template_debug
cmake --build build-cmake -j8
```

Цель `godot-cpp` создаётся как STATIC и имеет алиас `godot::cpp`; её
include-каталога объявлены PUBLIC, поэтому подключать их вручную не нужно.

**Статус этого файла:** он сверен с исходниками `godot-cpp`
(`cmake/godotcpp.cmake`), но **не проверен фактической сборкой** — в среде,
где он написан, `cmake` отсутствует. Проверка выполняется заданием CI
`cmake-smoke`, которое собирает проект и сверяет имя результата с
объявленным в `.gdextension`.

CMake даёт то, чего не даёт SCons: `compile_commands.json`, благодаря
которому CLion и clangd видят настоящие флаги сборки. Автодополнение и
диагностика в IDE совпадают с реальной компиляцией, а не угадываются.

Universal-сборка для macOS через CMake **не поддерживается** (scons вызывает
`lipo` вручную) — для macOS используйте scons.

### Локальная проверка без полной сборки

```bash
bash tools/cpp/syntax_check.sh --objects
```

Компилирует каждую единицу трансляции до объектного файла. Это не линковка,
но ловит все ошибки, которые вообще способен поймать компилятор.

Полная сборка `godot-cpp` — около тысячи единиц трансляции; в среде с двумя
ядрами и 3 ГБ памяти она нереальна. Линковка проверяется в CI.

## Флаги компиляции: два обязательных правила

**RTTI отключать НЕЛЬЗЯ.** `godot::Object::cast_to<T>()` внутри godot-cpp
реализован через `dynamic_cast` (`include/godot_cpp/core/object.hpp:133`).
С `-fno-rtti` код компилируется, но `cast_to` возвращает мусор или падает в
рантайме. Выглядит это как «движок сломался», а причина — во флаге.

**Исключения отключать можно.** `-fno-exceptions` используется самим
godot-cpp, и зеркалить этот флаг безопасно.

**Точность float обязана совпадать с точностью сборки движка.** Расхождение
по `float=64` ломает ABI: расширение загружается неверно или не загружается
вовсе.

## Версии

| Что | Значение | Почему |
| --- | --- | --- |
| Целевой Godot | 4.7.2-stable | актуальный стабильный на момент написания |
| Подмодуль `godot-cpp` | тег `godot-4.5-stable` | последний тег ветки 4.5 |
| `compatibility_minimum` | `4.5` | см. ниже |
| `reloadable` | `true` | правка C++ не требует перезапуска редактора |

**Почему собираемся против 4.5, а не против 4.7.**

ABI GDExtension обратно совместимо: расширение, собранное против 4.5,
работает на 4.5, 4.6 и 4.7. Обратное неверно — сборка против свежей версии
может использовать символы, которых в 4.5 нет, и тогда расширение упадёт при
загрузке на более старом движке.

Поэтому собирают против **старейшей поддерживаемой** версии и получают
совместимость со всеми следующими. Тесты в CI тоже прогоняются на 4.5
(блокирующее задание), а на последней версии — отдельно и
неблокирующе, чтобы заметить будущую поломку заранее.

`compatibility_maximum` намеренно не задан: верхняя граница отрезала бы
будущие версии движка без всякой причины.

## Самая опасная ошибка

**Расширение собралось, но игра его не видит — и не сообщает об этом.**

Если имя файла не совпадает с объявленным в `.gdextension`, Godot просто не
находит библиотеку. Он не падает и не пишет ошибку: `DestructionService`
обнаруживает отсутствие класса через `ClassDB.class_exists()` и молча
переключается на GDScript-запасной путь. Игра работает, но медленнее, и никто
не понимает почему.

Защита — сверка фактических файлов в `game/bin/` с объявленными. Она
выполняется в CI (задания `build-extension` и `cmake-smoke`) для каждой
платформы отдельно, потому что суффикс формируется из платформы, таргета и
архитектуры.

## Сторонний код: подмодуль или вендоринг

В проекте два разных способа подключения стороннего кода, и выбор не
случаен.

| Компонент | Способ | Почему |
| --- | --- | --- |
| `gdextension/godot-cpp` | **git-подмодуль** | зависимость времени сборки, привязана к тегу `godot-4.5-stable`. Версия обязана совпадать с `compatibility_minimum`, поэтому закрепляется коммитом |
| `game/addons/gut/` | **вендоренные файлы** | это конвенция Godot: дополнения устанавливаются копированием каталога `addons/` в проект. Игра обязана открываться и запускать тесты без сети |

```bash
git submodule update --init --recursive   # для godot-cpp
```

`tools/setup/setup.sh` выполняет и подключение подмодуля, и раскладку GUT из
архива codeload — идемпотентно, поэтому повторный запуск не ломает
существующее окружение.

Версия GUT фиксируется в `game/addons/gut/plugin.cfg` (`version="9.6.1"`), а
лицензия лежит рядом — `game/addons/gut/LICENSE.md`. Каталог помечен в
`.gitattributes` как `linguist-vendored=true`, поэтому GitHub не учитывает его
в статистике языков и в blame.
