# Решения проблем

Здесь собраны ошибки, которые **реально случились в этом проекте** и были
воспроизведены, поняты и исправлены. Каждая записана в форме
«симптом → причина → решение», потому что искать по симптому, а не по
причине.

Отличие от обычного списка советов: ни один пункт не придуман заранее. Если
симптом не совпадает с описанным, причина, скорее всего, другая.

## Движок и проект

### `Engine.has_singleton("GameConfig")` возвращает `false`

Autoload — **не** синглтон движка. Это обычный узел в дереве по пути
`/root/GameConfig`, добавленный движком при запуске. Обращаться к нему нужно
по имени узла или через предзагруженную ссылку, но не через `Engine`.

### Настройка из `project.godot` не применяется

Проверьте, что имя совпадает **полностью**, включая префикс раздела.
`godot_api_check.py` знает стандартные префиксы (`rendering/`, `physics/`,
`audio/`, `display/`, `input_devices/`, `textures/`, …) и помечает
нестандартные как подозрительные.

Ошибочные имена, встречавшиеся в проекте:

| Неверно | Верно |
| --- | --- |
| `rendering/anti_aliasing/default_anisotropic_filtering` | через `RenderingServer` такого метода нет вообще |
| `rendering/limits/decals/max_visible` | такого пути нет |
| `DirectionalLight3D.DirectionalShadowMode` | `DirectionalLight3D.ShadowMode` |
| `Environment.BackgroundMode` | `Environment.BGMode` |
| `Environment.ToneMapper` — перечисление | `Environment.ToneMapper` (совпадает) |

### Свойство существует, но не работает

Часть настроек применяется только через `RenderingServer`, а не через
`ProjectSettings`. И наоборот: у `RenderingServer` нет
`set_default_anisotropic_filtering` — метод кажется очевидным по аналогии,
но его не существует. Проверяйте наличие по
`gdextension/godot-cpp/gdextension/extension_api.json`: это точный список API
версии 4.5.stable.

Полезные факты из того же файла:

- связь с родителем у класса — поле `inherits`, а **не** `super`;
- сигналы класса лежат **отдельным** списком, а не внутри `methods`;
- `values` у перечисления — список словарей `{"name","value"}` внутри
  `classes`, но обычный словарь внутри `global_enums`;
- `new()` в списке методов отсутствует, хотя работает.

## GDScript

### `Unexpected token REGULAR_STRING`

GDScript **не поддерживает** неявную склейку строковых литералов через
перенос строки, в отличие от C и Python:

```gdscript
# НЕ РАБОТАЕТ
var text := "первая часть "
        "вторая часть"

# РАБОТАЕТ
var text := "первая часть " + "вторая часть"
```

### `gdlint` требует табуляцию

Формат проекта — табы (`tab-characters: 1` в `.gdlintrc`, `.editorconfig`).
Писать код пробелами и приводить позже — рабочий способ:
```bash
python3 tools/lint/normalize_gdscript.py --write
```

### `gdparse`/`gdlint`/`gdformat` не принимают каталог

Только список файлов. Используйте обёртку:
```bash
bash tools/lint/lint_gdscript.sh          # проверка
bash tools/lint/lint_gdscript.sh --fix    # автоформатирование
```

### `gdlint` проверяет тесты по продакшен-правилам

У `gdlint` **нет флага пути к конфигу** — он ищет `.gdlintrc` от текущего
каталога вверх. Чтобы применить разные правила к коду и к тестам, нужен
отдельный конфиг и отдельный рабочий каталог: `game/tests/.gdlintrc`
повышает `max-public-methods` до 80 (в тестовом классе десятки `test_*` —
норма, а не запах). `lint_gdscript.sh` разделяет прогон на два именно поэтому.

### `class-definitions-order`

Порядок объявлений в файле проверяется строго:
`tools → classnames → extends → docstrings → signals → enums → consts →
staticvars → exports → pubvars → prvvars → onreadypubvars → onreadyprvvars →
others`.

`const` после `func` — ошибка. Это не косметика: при таком порядке класс
читается сверху вниз как «что это → чем управляет → что делает».

### Файл длиннее 700 строк

Разделяйте, а не поднимайте лимит. В проекте так и сделали:
`settings_service.gd` (876 строк) → сервис + `settings/settings_schema.gd`.
Разделение оказалось содержательным: схема настроек — чистые данные, и
форма интерфейса строится по ней без участия сервиса.

### `max-returns: 6`

Больше шести `return` в функции — признак того, что функция делает несколько
дел. В проекте лимит не поднимали ни разу; вместо этого разбирали ветвления.

### `gdformat` переносит длинные вызовы и ломает статический анализ

Форматировщик оборачивает длинные цепочки и литералы словарей в скобки и
переносит их на несколько строк. Анализ, работающий построчно, после этого
видит вызов разорванным.

Решение двойное: держать места вызова короткими и учить анализатор
переносам. В `check_backend_contract.py` пришлось обрабатывать три случая:
сканер оказывается **внутри незакрытой кавычки**, строка начинается с запятой
(первая «часть» пуста → арность 8 вместо 7), и параметр задан константой
`PARAM_*`, а не литералом `&"wind_…"`.

### `boolean` — не тип

В GDScript тип называется `bool`. Аннотация `-> boolean` падает на разборе.

### `sqrtf()` не существует

Есть только `sqrt()`. Суффиксы `f` для float-версий математических функций
пришли из C и в GDScript не перенесены.

## Сцены и узлы

### Главное меню не показывает 3D-фон

Сцена, укоренённая в `Control`, ненадёжно отображает 3D-содержимое. Корень
должен быть `Node`, а внутри — `Node3D` с фоном и `CanvasLayer` с
интерфейсом.

### `load_steps` в `.tscn`

Godot **опускает** строку `load_steps`, когда внешних и внутренних ресурсов
нет вовсе. В остальных случаях `load_steps = внешние + внутренние + 1`.
Проверка сцен обязана учитывать оба случая, иначе каждая сцена без ресурсов
выглядит повреждённой.

### `process_mode` у меню паузы

Значение `3` (`PROCESS_MODE_ALWAYS`) должно стоять **в `.tscn`**, а не
выставляться кодом в `_ready()`: до первого кадра узел уже может получить
событие, и меню паузы окажется замороженным вместе с игрой.

### `Area3D` не обнаруживается лучом

`RayCast3D` с `collide_with_areas` требует у цели `monitorable = true`. Без
этого луч проходит сквозь область, и взаимодействие «не работает» без единой
ошибки в логе.

### Луч попадает не в тот узел

`RayCast3D` возвращает `CollisionShape3D` или `Area3D`, а не узел с игровой
логикой. Нужно подниматься по родителям до узла с нужным методом или
группой — обращение к логике напрямую даёт `null`.

### Изменение слоя физики внутри физического колбэка не срабатывает

Используйте `set_deferred()`. Прямое присваивание в середине шага физики
игнорируется без сообщения.

### `is_on_floor()` пропадает на кадре при движении по склону

`CharacterBody3D` нужно небольшое отрицательное `velocity.y` на полу. При
нулевой вертикальной скорости тело формально отрывается, и проверка
возвращает `false` на один кадр — прыжок «не срабатывает» на подъёме.

### Обводка объекта не видна

Используйте `material_overlay`, а не `material_override`. Последний заменяет
материал целиком, и объект теряет собственную текстуру.

### `get_world_3d()` недоступен

Метод есть у `Node3D`, но не у `Node`. Если сцена укоренена в `Node` (что
нужно для 3D-фона меню), к миру надо обращаться через конкретный
3D-потомок.

### `MeshDataTool.create_from_surface` не принимает `Mesh`

Нужен `ArrayMesh`. Для примитивов (`BoxMesh`, `SphereMesh`) сначала
`SurfaceTool.create_from(mesh, i)`, затем `commit(array_mesh)`.

### Число треугольников в `BoxMesh` равно нулю

У примитивов **пустой** `ARRAY_INDEX` — геометрия неиндексированная. Считать
треугольники нужно по `ARRAY_VERTEX`, а не по индексам.

### Узел из `boot.tscn` не виден в других сценах

Это обычный узел дерева, а не autoload. Всё, что должно быть доступно
отовсюду, обязано быть в списке autoload в `project.godot`.

## Интерфейс

### Нужна кликабельная ссылка, а `LinkLabel` не находится

В Godot **нет** `LinkLabel`. Два рабочих варианта:

- плоская `Button` — заодно получает фокус, поэтому меню управляемо с
  клавиатуры и геймпада;
- `RichTextLabel` с bbcode `[url=…]` и сигналом `meta_clicked`.

### `CanvasLayer` не меняет прозрачность

У `CanvasLayer` **нет** свойства `modulate` — оно у `CanvasItem`. Плавное
появление слоя делается через `Control` внутри него либо анимацией
`layer`/`offset`.

### `Theme.set_stylebox()` не принимает строку

Нужен объект `StyleBox`. Передача имени типа (`"Panel"`) — типичная ошибка,
которая выглядит как «тема не применяется».

### Строка интерфейса осталась без подписи

Проверяется тестом: каждая строка формы настроек обязана иметь подпись, а имя
строки не должно содержать `/`. Без этого требование «профессиональный GUI»
не проверяемо ничем.

## Шейдеры

### Вода считается неправильно на расстоянии

Во фрагментной стадии `spatial`-шейдера `VERTEX` задан **в пространстве
вида**, поэтому линейное расстояние до камеры — это `-VERTEX.z`. Попытка
взять длину `VERTEX` даёт расстояние от начала координат вида, а не от
камеры.

### `render_mode world_vertex_coords` ломает расчёты

Режим **молча** меняет пространство, в котором задан `VERTEX`. Все формулы,
рассчитанные на пространство вида, перестают работать без всякой ошибки.

### Линтер шейдеров считает локальные переменные необъявленными

Наивный разбор видит обращение к имени и, не найдя `uniform`, объявляет его
неизвестным. Правильный порядок: сначала собрать локальные переменные,
константы, `uniform`, параметры функций и структуры, **затем** проверять
обращения.

### Глобальный параметр не доходит до шейдера

Глобальные shader-параметры объявляются обычным `uniform` и сопоставляются
**по имени**. Ключевого слова `global` в языке нет, и отличить глобальный
параметр от поля материала по синтаксису невозможно. Опечатка в имени — это
не ошибка компиляции, а молча неработающий эффект.

Именно поэтому `check_backend_contract.py` сверяет имена параметров ветра
между `WindSystem` и шейдерами. Исключение, закреплённое в проверке:
`wind_response` намеренно является uniform-переменной **материала**, а не
глобальным параметром.

### Подсказки sampler'ов

Рабочий набор: `hint_screen_texture`, `hint_depth_texture`,
`filter_linear_mipmap`, `repeat_enable`, `source_color`. В `shader_type sky`
доступны `EYEDIR` и `COLOR`.

## C++ и GDExtension

### Расширение собралось, но игра его не видит

Самая опасная ошибка раздела. При несовпадении имени файла с объявленным в
`.gdextension` Godot **не падает и не пишет ошибку**: он просто не находит
библиотеку, а `DestructionService` через `ClassDB.class_exists()` молча
переключается на GDScript-запасной путь. Игра работает, но медленнее.

Защита — сверка фактических файлов в `game/bin/` с объявленными (задания CI
`build-extension` и `cmake-smoke`).

Шаблон имени: `libnewwoorld.<platform>.<target>[.dev][.double].<arch><ext>`.

### `cast_to<T>()` возвращает мусор

RTTI отключать **нельзя**: `godot::Object::cast_to<T>()` реализован через
`dynamic_cast` (`include/godot_cpp/core/object.hpp:133`). С `-fno-rtti` код
компилируется, но падает или врёт в рантайме. Исключения при этом отключать
можно — `-fno-exceptions` использует сам godot-cpp.

### Расширение работает на 4.5, но не на 4.7 (или наоборот)

Собирать нужно против **старейшей** поддерживаемой версии. ABI GDExtension
обратно совместимо: сборка против 4.5 работает на 4.5, 4.6 и 4.7. Обратное
неверно — сборка против свежей версии может использовать символы, которых в
4.5 нет.

Отсюда `compatibility_minimum = "4.5"` и закреплённый подмодуль на теге
`godot-4.5-stable`. Тесты в CI блокирующе прогоняются на 4.5.

### `Basis::xform_vector` не находится

Такого метода нет. Есть `xform()` и `xform_inv()`.

### `HashMap<Vector3i, …>` не компилируется

Для `Vector3i` нет хешера по умолчанию. Рабочее решение в проекте —
кодировать воксель в `int64_t` и использовать его ключом.

### Все типы движка не находятся

Они в `namespace godot`. Без `using namespace godot;` или полной
квалификации ни один тип не разрешится.

### `binding_generator.py` не принимает аргументы командной строки

У скрипта нет argparse. Импорт и вызов:
```python
import binding_generator
binding_generator.generate_bindings(...)
```

### Полная сборка не завершается на слабой машине

`godot-cpp` — около тысячи единиц трансляции. На двух ядрах и 3 ГБ памяти
сборка нереальна по времени. Локально достаточно
```bash
bash tools/cpp/syntax_check.sh --objects
```
а линковку проверяет CI.

## Инструменты проверки

### Проверка сообщает, что все действия ввода не привязаны

Значения в секции `[input]` файла `project.godot` — **многострочные блоки в
фигурных скобках**:
```ini
move_forward={
"deadzone": 0.2,
"events": [Object(InputEventKey, ...)]
}
```
Построчный парсер `ключ=значение` прочитает значение как `{` и решит, что
список событий пуст. Нужен подсчёт глубины скобок и накопление строк
продолжения до баланса. Реализовано в `check_data.parse_ini_sections()`.

### Шаг проверки «вечно красный», хотя всё установлено

Проверки обязаны различать «провал» и «инструмент недоступен». В
`verify_all.sh` код **125** означает недоступность и трактуется как ПРОПУСК,
а не как провал. Итоговый отчёт печатает пропуски отдельно и добавляет:
«пропущено N — это НЕ «всё хорошо»».

### `check_backend_contract.py` выдаёт ложные срабатывания

Четыре источника, все устранены. Возвращать их нельзя:

1. `WindSystem._add_param()` принимает константы `PARAM_*`, а не литералы
   `&"wind_…"` — сканер обязан их разыменовывать;
2. `gdformat` переносит `.call("fracture", …)` на несколько строк, и сканер
   оказывается внутри незакрытой кавычки;
3. перенос создаёт строку, начинающуюся с запятой, — первая часть пуста,
   арность получается 8 вместо 7;
4. `wind_response` — uniform материала, а не глобальный параметр.

### `godot_api_check.py` выдаёт десятки «неизвестный глобальный вызов» на GUT

Классы из `addons/` не индексировались. Флаги `--addons` / `--no-addons`
управляют индексацией `class_name` из каталога дополнений.

### Статический анализ не находит ошибку в ключах словаря

**Ни один из линтеров не проверяет ключи словарей.**
`snapshot.get("wrong_key")` вернёт `null` без ошибки, и интерфейс молча
покажет пустоту.

Реальный случай: оверлей отладки читал 10 ключей, которых не было в
`PerfMonitor.build_snapshot()`. Синтаксис верный, типы верные — данных нет.

Решение: вынести имена ключей в константы `K_*` и список `SNAPSHOT_KEYS` у
источника данных, а соответствием проверять контрактным тестом
(`test_debug_overlay_contract.gd`).

### Слепые зоны линтеров

| Что | Чем покрыто |
| --- | --- |
| Существование метода/свойства | `godot_api_check.py` |
| Число и типы аргументов | `gdscript_call_check.py` |
| Ключи словарей | только контрактные тесты |
| Строковые пути свойств (`tween_property(self, "modulate:a", …)`) | ничем — только рантайм |

### Патч-скрипт молча ничего не изменил

`str.replace()` в Python **не выдаёт ошибку**, если якорь не найден. Любой
скрипт, правящий исходники, обязан начинать с `assert old in s`. Иначе
получается «правка применена» при неизменном файле.

## Ассет-конвейер

Все ошибки этого раздела найдены собственными проверками конвейера
(`check_pipeline.mjs`), а не в бою. Подробный разбор — в
[`ASSET-PIPELINE.md`](ASSET-PIPELINE.md).

### `simplifier dependency required — install "meshoptimizer"`

Пакет установлен. Причина — опечатка в имени ключа: `simplifyor` вместо
`simplifier`. Лишний ключ опций **игнорируется молча**, поэтому ошибка
возникает позже и указывает не туда.

### `Method requires Uint8Array parameter; received "object"`

`NodeIO.readBinary()` принимает `Uint8Array`, а не `ArrayBuffer`. Передавать
`.buffer` нельзя и по второй причине: это взгляд на весь выделенный пул
памяти, и заголовок glTF оказывается прочитан со смещения.

### `generateTangents callback required — install "mikktspace"`

`tangents()` не умеет считать тангенты сам — ему нужен колбэк MikkTSpace.
Зависимость **не транзитивная**, поэтому объявлена в `package.json` явно.

### Тангенты молча не появляются

`tangents()` пропускает любой примитив, у которого **есть** индексы
(исходники пакета: *«primitives must be unwelded»*). Печатается только
`No qualifying primitives found`. Перед шагом геометрию нужно разварить.

`normals()` разваривает сам, но запускается только когда нормалей нет; если
они уже были, `unweld()` нужен явно.

### `reorder: No qualifying primitives found; may need to weld first`

Обратная ситуация: `reorder()` требует **сваренную** геометрию.

Порядок, проверенный измерением (модель 800 треугольников, текстура 1024²):

| Порядок | Результат |
| --- | --- |
| `quantize → reorder` | 693 948 байт, предупреждение |
| `weld → reorder → quantize` | 679 044 байт, чисто |

### `decodeGltfBuffer is not a function`

`MeshoptEncoder` подставлен на место декодера. Энкодер и декодер — разные
объекты: `decodeGltfBuffer` есть только у `MeshoptDecoder`. Установка
зависимостей при этом проходит успешно, а падает повторный прогон конвейера
по уже сжатой модели.

### `inspect()` возвращает `undefined` вместо примитивов

В `@gltf-transform` 4.5.1 отчёт — это `{scenes, meshes, materials, textures,
animations}`, каждый раздел со списком `.properties`. Поля `primitives` на
верхнем уровне нет. Треугольники — сумма `meshes.properties[].glPrimitives`.

### Версия пакета печатается как `() => validator.version()`

У `gltf-validator` `version` — **функция**, у `@gltf-transform/core` — строка.
Нужно приводить обе формы.

### Текстура исчезла после оптимизации

`prune({ keepSolidTextures: false })` заменяет однотонную текстуру
константным `baseColorFactor`. Для плоского цвета это оптимизация, а не
потеря. На неоднотонной текстуре поведение другое — проверено: она
сохраняется.

### KTX2 не кодируется

Кодирование требует внешних инструментов KTX-Software (`toktx`, `basisu`),
которых нет ни в среде разработки, ни в стандартном CI-раннере. Конвейер по
умолчанию использует WebP (кодируется установленным `sharp`, поддерживается
Godot 4 нативно). Флаг `--ktx2` оставлен для среды с полным тулчейном.

## Репозиторий и git

### `git check-ignore --stdin` возвращает код 128 и пустой результат

Так происходит, если **хотя бы один** путь в пакете лежит внутри подмодуля
(в проекте это `gdextension/godot-cpp`). При этом выбрасывается результат по
всему пакету, а не только по проблемному пути.

Решение: поштучный запасной путь и предварительное чтение `.gitmodules`,
чтобы вообще не сканировать деревья подмодулей — ими управляют собственные
правила подмодуля.

### В проверке гигиены висит предупреждение о мусоре, которого нет

Каталог игнорируется git, но проверка его видит. Фильтровать нарушителей
нужно через `git check-ignore` (с учётом поведения выше) и исключать
подмодули.

### Артефакты сборки попали в git

`.gitignore` обязан покрывать результаты сборки расширения. В проекте
добавлены `gdextension/*.wasm` и
`game/bin/*.{so,dll,dylib,wasm,pdb}` — с исключением
`!game/bin/*.gdextension`, потому что сам файл объявления является исходником
и должен отслеживаться.

### Скрипт не запускается напрямую

Точки входа обязаны иметь бит исполнения. Проверка
`check_repo_hygiene.py` контролирует `chmod +x` на четырёх `.sh`.

### `project.godot` разошёлся с генератором

Файл создаётся скриптом, но отредактировать его руками возможно — и редактор
Godot делает это сам при любом изменении настроек проекта. Правка не ломает
игру сразу: она молча расходится с генератором и стирается при следующей
генерации.

```bash
python3 tools/setup/generate_project_godot.py --check   # сверить
python3 tools/setup/generate_project_godot.py           # перегенерировать
```

`--check` печатает конкретные разошедшиеся строки, а не просто «файлы
отличаются».

## Ограничения среды разработки

Факты, установленные проверкой, а не предположением. Их полезно знать, чтобы
не тратить время на заведомо невозможное.

**Доступно:** `gcc`/`g++`/`cc`, `make`, `python3` 3.11, `node` v22, `npm` 10.
Доступ к `github.com`, `codeload.github.com`, `api.github.com`,
`registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org`.

**Недоступно:** `clang`, `cmake`, `rustc`, `wine`, `mono`/`dotnet`,
`mingw-w64`, дисплей, бинарник Godot. Ресурсы: 2 ядра, 3 ГБ памяти, 20 ГБ
диска.

**Заблокировано:** загрузка файлов релизов GitHub
(`/releases/download/…` → `302` → `objects.githubusercontent.com` → соединение
не устанавливается). Это закрывает установку редактора Godot, Electron,
Tauri и mingw.

**Работает:** `git clone` с github.com, архивы через `codeload.github.com`,
npm, PyPI.

### Следствия

| Невозможно локально | Где выполняется |
| --- | --- |
| Запуск и отладка игры | машина с Godot |
| Прогон тестов GUT | CI, задание `tests` |
| Экспорт готовой сборки | CI / машина с шаблонами экспорта |
| Полная сборка GDExtension | CI, задание `build-extension` |
| Сборка CMake | CI, задание `cmake-smoke` |
| Кросс-компиляция под Windows | CI, раннер `windows-2022` |

Локально выполняется вся статическая проверка — и она же выполняется в CI,
тем же набором команд. Это осознанное дублирование: если локальный
`verify_all.sh` зелёный, а CI красный, расхождение между ними — само по себе
баг.
