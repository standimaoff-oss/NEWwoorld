# Проверки

Что именно проверяется, зачем, и что делать, когда проверка упала.

---

## Одна команда

```bash
bash tools/verify/verify_all.sh              # всё доступное
bash tools/verify/verify_all.sh --quick      # только линтеры, ~10 секунд
bash tools/verify/verify_all.sh --strict     # предупреждения = ошибки
bash tools/verify/verify_all.sh --with-godot # плюс импорт и прогон GUT
```

Через `make`: `make check`, `make quick`, `make strict`, `make verify`,
`make test`. Полный список целей: `make help`.

---

## Три исхода, а не два

Каждый шаг завершается одним из трёх состояний:

| Состояние | Код | Смысл |
| --- | --- | --- |
| ПРОЙДЕНО | 0 | Проверка выполнена, нарушений нет |
| ПРОВАЛ | 1…124 | Проверка выполнена, найдены нарушения |
| ПРОПУЩЕНО | **125** | Инструмент недоступен, проверить не удалось |

Разделение обязательно. Если «инструмент не установлен» считать провалом,
прогон вечно красный и его перестают читать. Если считать успехом —
пропускаются настоящие ошибки, и доверие к зелёному результату пропадает.

Итоговый отчёт печатает пропуски отдельной строкой и добавляет:
«пропущено N — это НЕ «всё хорошо»».

## Шаги

### 1. GDScript: синтаксис, формат, стиль, API, вызовы

`bash tools/lint/lint_gdscript.sh` — пять стадий внутри:

1. `gdparse` — синтаксис. Не проходит: код не загрузится вообще.
2. `gdformat --check` — форматирование. Чинится автоматически:
   `bash tools/lint/lint_gdscript.sh --fix`.
3. `gdlint` — стиль. **Продакшен и тесты проверяются раздельно**, потому что
   `gdlint` ищет конфиг от текущего каталога вверх и не имеет флага пути к
   конфигу. Для тестов существует отдельный `game/tests/.gdlintrc` с
   `max-public-methods: 80` (в тестовом классе десятки `test_*` — это норма,
   а не запах).
4. `tools/lint/godot_api_check.py` — существование API: вызываемые методы,
   свойства и константы действительно есть в движке 4.5
   (`extension_api.json`) или объявлены в проекте. Индексирует `class_name`
   из `addons/`, иначе GUT-классы выглядят неизвестными.
5. `tools/lint/gdscript_call_check.py` — **число и типы аргументов**.
   Написан специально для этого проекта после случая, когда оверлей читал из
   снимка метрик 10 ключей, которых там не было: синтаксис верный, типы
   верные, а данные — `null`, и интерфейс молча показывал пустоту.

Стадии 4 и 5 не заменяют друг друга: 4-я не знает арность вызова, 5-я не
проверяет существование свойства. И **ни одна из них не проверяет ключи
словарей** — `snapshot.get("wrong_key")` вернёт `null` без ошибки. Это
покрывают контрактные тесты (`test_debug_overlay_contract.gd`).

### 2. Сцены и ресурсы

`python3 tools/lint/godot_scene_check.py --strict`

Проверяет `.tscn`/`.tres`: заголовок `load_steps` (в Godot он равен
числу внешних + внутренних ресурсов плюс один, а при нуле ресурсов строка
отсутствует вовсе), ссылки на существующие файлы, наличие `ext_resource` для
каждого `sub_resource`-родителя. Каталог `addons/` пропускается — это чужой
код со своими соглашениями.

### 3. Шейдеры

`python3 tools/lint/shader_check.py`

Синтаксис `.gdshader` и соглашения проекта. Нюанс реализации: наивный
линтер считает локальные переменные, константы и параметры функций
необъявленными uniform-переменными. Поэтому разбор сначала собирает
`local`, `const`, `uniform`, параметры и структуры, и только потом проверяет
обращения.

### 4. Контракт бэкендов разрушения

`python3 tools/verify/check_backend_contract.py --strict`

Сверяет C++ и GDScript по трём осям:

- **форма данных**: ключи словаря, возвращаемого `NewwoorldFracturer.fracture()`,
  совпадают с `DestructionService.PIECE_KEYS`;
- **аргументы вызова**: GDScript передаёт в `.call("fracture", …)` ровно те
  параметры, которые принимает C++;
- **параметры ветра**: имена, которые `WindSystem` публикует как глобальные
  shader-переменные, совпадают с именами `uniform` в шейдерах.

Написан после реальной ошибки: C++ возвращал куски с ключом `voxel`,
GDScript — без него. Оба бэкенда работали, а игра вела себя по-разному в
зависимости от того, загрузилось расширение или нет.

Четыре источника ложных срабатываний, которые уже устранены и которые нельзя
возвращать:

- `WindSystem._add_param()` принимает константы `PARAM_*`, а не литералы
  `&"wind_…"` — сканер обязан их разыменовывать;
- `gdformat` переносит `.call("fracture", …)` на несколько строк, и наивный
  сканер оказывается **внутри незакрытой кавычки**;
- перенос создаёт строку, начинающуюся с запятой, — первая «часть» пуста, и
  арность получается 8 вместо 7;
- `wind_response` намеренно является uniform-переменной материала, а не
  глобальным параметром.

### 5. Данные

`python3 tools/verify/check_data.py`

- `game/data/credits.json` — обязательные разделы, непустые контакты,
  лицензии ассетов, атрибуция требует реального автора;
- `game/.gutconfig.json` — каталоги существуют и содержат тесты;
- `game/project.godot` — главная сцена, все 11 путей autoload, непустые
  input action, ни одной висячей ссылки `res://`;
- `game/resources/quality/*.tres` — бюджеты не убывают от low к ultra;
- **списки лицензий читаются из `game/scripts/util/validators.gd`**, а не
  дублируются. Раньше они были скопированы сюда с комментарием «совпадают с
  Validators.FREE_LICENSES», и комментарий врал: сверки не существовало,
  поэтому добавление лицензии в GDScript не меняло поведение проверки.

Нюанс разбора: значения в `project.godot` бывают **многострочными блоками в
фигурных скобках**:
```ini
move_forward={
"deadzone": 0.2,
"events": [Object(InputEventKey, ...)]
}
```
Построчный парсер `ключ=значение` прочитает значение как `{` и затем объявит
каждое действие ввода непривязанным. Нужен подсчёт глубины скобок и
накопление строк продолжения.

### 6. Гигиена репозитория

`python3 tools/verify/check_repo_hygiene.py`

- в git не отслеживаются артефакты сборки;
- все обязательные файлы на месте (27 позиций, включая `ТЗ.md`);
- `.gitignore` покрывает 9 шаблонов, `.gitattributes` — LFS;
- в рабочем дереве нет мусора;
- точки входа исполняемые (`chmod +x` на четырёх `.sh`).

Два подводных камня в реализации:

- `git check-ignore --stdin` завершается с кодом **128**, если хотя бы один
  путь лежит внутри подмодуля (`gdextension/godot-cpp`), и при этом
  выбрасывает результат **по всему пакету**. Нужен поштучный запасной путь.
- Каталоги подмодулей не сканируются на мусор вообще — ими управляют
  собственные правила подмодуля.

### 7. Ассет-конвейер

`node tools/asset-pipeline/scripts/check_pipeline.mjs` — 24 проверки.
Подробности в [`ASSET-PIPELINE.md`](ASSET-PIPELINE.md).

### 8. C++

`bash tools/cpp/syntax_check.sh --objects` — компиляция каждой единицы
трансляции до объектного файла.

Это **не полная сборка**: godot-cpp — около тысячи единиц трансляции, и
слинковать расширение в среде с 2 ядрами и 3 ГБ памяти нереально. Линковка
проверяется в CI (задание `build-extension`). Локально же ловятся все ошибки,
которые вообще может поймать компилятор: неизвестные типы, неверные
сигнатуры, пропущенные заголовки.

### 9. Тесты GUT (только `--with-godot`)

Импорт проекта + прогон GUT. Без бинарника Godot шаг пропускается с кодом
125, и это честно: тесты не выполнены.

## Когда проверка упала

| Симптом | Действие |
| --- | --- |
| `gdformat` ругается | `bash tools/lint/lint_gdscript.sh --fix` |
| `gdlint`: `class-definitions-order` | Переставьте объявления. Порядок строгий: `tools`, `classnames`, `extends`, `docstrings`, `signals`, `enums`, `consts`, `staticvars`, `exports`, `pubvars`, `prvvars`, `onreadypubvars`, `onreadyprvvars`, `others`. `const` после `func` — ошибка |
| `gdlint`: `max-file-lines` | Разделяйте файл, а не поднимайте лимит. В проекте так уже сделали: 876 строк → `settings_service.gd` + `settings_schema.gd` |
| `godot_api_check`: неизвестный метод | Либо опечатка, либо метод появился в другой версии движка. Сверьтесь с `gdextension/godot-cpp/gdextension/extension_api.json` |
| `call_check`: арность | Сигнатура изменилась — обновите все места вызова, а не проверку |
| `check_data`: расхождение `project.godot` | `python3 tools/setup/generate_project_godot.py` |
| `check_repo_hygiene`: нет обязательного файла | Создайте файл. Список в константе `REQUIRED_FILES` |
| Шаг ПРОПУЩЕН | Поставьте инструмент: `bash tools/setup/setup.sh` |

## Чего проверки не делают

- **Не запускают игру.** Для этого нужен Godot и, для экспорта, шаблоны.
- **Не собирают расширение целиком.** Только синтаксис и объектные файлы.
- **Не измеряют производительность.** Есть бюджеты (числа в ресурсах), но нет
  замеров: на CI раннер каждый раз другой, и порог по времени давал бы
  случайные провалы.
- **Не оценивают визуальное качество.** Требование ТЗ «не AI slop»
  проверяется человеком при просмотре. Косвенно его прикрывают бюджеты сцен
  и запрет на HDRI-панорамы в меню.
