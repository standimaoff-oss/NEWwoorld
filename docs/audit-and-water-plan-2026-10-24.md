## 5. Готовность к новому моду

Сейчас в репозитории фактически пусто: только `README.md`. Для Forge 1.20.1 нужно создать с нуля:

- Gradle + ForgeGradle 6, Java 17, wrapper;
- `mods.toml`, `pack.mcmeta`, основной класс мода;
- структуру `src/main/java`, `src/main/resources`;
- CI на GitHub Actions (сборка jar);
- mixin-конфиг и тестовый harness.

Старые Forge 1.20.1-заготовки (Gradle wrapper, workflow-файлы, `mods.toml`) есть в бэкапе — их можно переиспользовать, чтобы не настраивать всё заново.

### Ограничение среды сборки

В этой песочнице исходящий доступ разрешён только к GitHub, npm и PyPI. Maven-репозитории Forge/Minecraft (`maven.minecraftforge.net`, `libraries.minecraft.net`) недоступны, поэтому **локально собрать Forge-мод здесь нельзя**. Рабочая схема — писать код и собирать его в GitHub Actions, как это уже делалось в старых ветках. При старте надо будет проверить, что токену разрешено пушить workflow-файлы (сейчас у него нет `actions: write`, но пуш кода/воркфлоу может работать).

## 6. Мод физической воды: техническая концепция

### 6.1 Что именно требуется

- Forge 1.20.1, Java 17.
- Объёмная вода, а не кубическая: плавная поверхность, наклонные/закруглённые формы, а не блоки.
- Нет бесконечного источника: масса воды конечна и сохраняется.
- Полная замена ванильной воды.
- Если выкопать яму — вода стекает в неё; можно вылить/осушить целую небольшую реку.
- Полная физика: течение, водопады, волны от игрока (несильные), плавание, лодки.
- Красиво: преломление, отражения, пена, каустика, глубина/поглощение света.
- Настройки 16 / 32 / 64 бита.
- Профессиональная оптимизация.

### 6.2 Честно о сложности

Это не «мод на пару дней». Ванильная вода — это блок-состояния и `FlowingFluid`, а не объёмная жидкость. Полная замена затрагивает генерацию мира, океаны, дождь, лёд, вёдра, плавание, лодки, рыбалку, кораллы, лаву, редстоун, освещение, звук и сохранения. Технически всё это реализуемо, но правильный путь — поэтапно: сначала конечная вода с плавным рендером и волнами, затем 3D-объёмы и полная замена.

### 6.3 Архитектура

Предлагаю гибридный солвер — он даёт нужное поведение при играбельной производительности:

1. **2.5D shallow-water для больших поверхностей**  
   Сетка высот воды + 2D-скорость на суб-блочной сетке (4×4 или 8×8 ячеек на блок). Реки, озёра, океаны, стекание в ямы, осушение рек. Консервативный перенос массы, давление/проекция, трение о дно, wet/dry фронты.
2. **Локальный 3D-солвер для объёмных мест**  
   MAC-сетка / FLIP-подход в активной области вокруг игрока: водопады, пещеры, вертикальные потоки, ямы с перекрытиями. Связь с 2.5D-слоем двусторонняя.
3. **Конечная масса**  
   Никакого создания воды из двух источников. Источники — это конечные резервуары/потоки (дождь, родник, река), настраиваемо. Океан можно сделать граничным условием или очень большим конечным резервуаром — это отдельное решение.
4. **Взаимодействие с миром**  
   Воксельный SDF/коллизии блоков, вода не проходит сквозь твёрдые блоки, выталкивается ими; сущности получают плавучесть/сопротивление; лодки и плавание используют скорость течения.
5. **Волны от игрока**  
   Импульс скорости/вытеснение в радиусе + затухающая волновая модель; след за игроком/лодкой, пена у кромки. Сила настраивается, чтобы волны были «не сильные».
6. **Рендер**  
   Сетка поверхности из поля высот (гладкие нормали, без кубов) + marching cubes/dual contouring для 3D-объёмов. Шейдеры: преломление, отражения (SSR + cubemap fallback), Fresnel, поглощение по глубине, каустика на дне, пена, flow-map нормали, мягкие края. LOD и half-res проходы.
7. **Замена ванильной воды**  
   Mixin'ы в `WaterFluid`/`FlowingFluid`, тик жидкости, `LiquidBlockRenderer`, генерацию источников, океаны/аквиферы. Ванильный блок `minecraft:water` можно оставить как «носитель» для совместимости (плавание, свет, id), но рендер, течение и источники полностью перехватываются. Это функциональная полная замена без тотального удаления блока, которое сломало бы другие моды.
8. **Сеть и сохранения**  
   Сервер авторитетен; клиент получает сжатые тайлы высот/скоростей и интерполирует. `SavedData` по чанкам, версионирование, асинхронная загрузка/выгрузка, дельта-обновления. Локальные волны предсказываются на клиенте.
9. **Оптимизация**  
   Активная область только вокруг игроков, sleep для устоявшейся воды, многопоточный солвер, GPU compute (OpenGL 4.3+) с CPU-fallback, фиксированный тик 30 Гц с интерполяцией, бюджет времени на сервере/клиенте, асинхронный мешинг, отсутствие per-block TESR, профилирование (Spark/JFR), бенчмарки.

### 6.4 Пресеты 16 / 32 / 64 бита

Пока трактую это как **точность симуляции**:

| Пресет | Точность | Для чего |
|---|---|---|
| 16 бит | half/fixed-point, меньше памяти | слабые ПК, большие серверы, быстрый режим |
| 32 бита | float, по умолчанию | баланс качества и производительности |
| 64 бита | double, ultra | максимальная точность, большие координаты, скриншоты/кино |

Графическое качество (низкое/среднее/высокое/ultra) лучше сделать отдельной настройкой, независимой от точности физики. Если под «16/32/64 бита» имелась в виду битность текстур/цвета или что-то ещё — уточните, подстрою архитектуру.

### 6.6 Риски

- Полная замена воды ломает другие моды и ванильные механики (фермы, рыба, кораллы, лёд, редстоун).
- Производительность на серверах: Java-солвер надо жёстко бюджетировать; GPU compute есть не у всех (на macOS OpenGL 4.1, compute недоступен).
- Совместимость с OptiFine/Iris и шейдерпаками.
- Сохранения и миграция: старые миры с ванильной водой.
- «Нет бесконечного источника» меняет баланс: океаны/реки должны откуда-то брать воду; нужна настройка.
- Объёмная вода против блочных коллизий: игроку нужна понятная форма столкновения/плавания.

### 6.7 Что нужно решить до старта

1. **16/32/64 бита** — это точность симуляции, битность текстур/цвета или что-то третье?
2. **Глубина замены** — вся вода в мире (океаны, дождь, аквиферы, лёд) или только динамическая/игровая вода? Полная замена — самый большой риск совместимости.
3. **Целевая производительность** — одиночная игра, сервер на N игроков, слабые ПК? Какой масштаб «небольшой реки» (например, 100×100 блоков)?
4. **Визуальный уровень** — ванильный стиль с реалистичной водой или «прямо кино» с шейдерами? Нужна ли работа без OptiFine/Iris?
5. **Название и modid** нового мода, и оставляем ли репозиторий `NEWwoorld` или создаём отдельный (работа в этой сессии всё равно идёт в текущей ветке).
6. **Совместимость** — только ванилла или приоритет на Create, Flywheel и другие популярные моды?
