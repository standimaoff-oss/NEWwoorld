# Техническое задание на создание игры

**Проект:** NEWwoorld
**Движок:** Godot Engine 4.x (целевая версия 4.7.2-stable, сборка против 4.5)
**Документ для:** ИИ-агента, который создаёт игру в этом репозитории
**Статус:** обязательный к исполнению

---

## Как пользоваться этим документом

Это не список пожеланий. Каждое требование здесь либо **проверяется
инструментом**, либо **имеет числовой порог**, либо объясняет, **какая
конкретно ошибка** произойдёт при нарушении. Требование без проверки — не
требование, а намерение; намерения в производстве не выполняются.

Три правила чтения:

1. **«Должно» — обязательно.** Отклонение требует записанного решения с
   причиной, а не молчаливого пропуска.
2. **Примеры — не требования.** Там, где приведён конкретный приём
   (процедурное небо, ветер в листве), это иллюстрация подхода. Исполнитель
   свободен предложить своё решение, если оно удовлетворяет требованию и
   бюджету.
3. **Числа — это бюджеты, а не цели.** Превышение бюджета — ошибка. Значимое
   недостижение бюджета (например, меню на 12 узлов вместо 512) — тоже
   ошибка: оно означает, что требование к качеству не выполнено.

Инфраструктура, реализующая проверку этих требований, уже существует.
Перечень — в разделе [«Проверка и приёмка»](#проверка-и-приёмка).

<a id="1-общий-принцип"></a>
## 1. Общий принцип

### Требование: не должно быть «AI slop»

Требование субъективно, поэтому переводится в проверяемые признаки.
«AI slop» — не стиль, а **набор конкретных дефектов**, каждый из которых
определяется объективно:

| Признак | Как проявляется | Чем проверяется |
| --- | --- | --- |
| Несоответствие масштабов | дверь высотой 1 м, стул выше игрока | бюджет сцены + ревью |
| Пустое пространство | большая сцена, где ничего не происходит | ревью |
| Одинаковые объекты без вариаций | 200 идентичных ящиков в ряд | ревью |
| Освещение «в лоб» | один источник света, плоские тени | число источников в сцене |
| Дефолтные материалы | серый пластик на всём | число уникальных материалов |
| Отсутствие следов использования | мир выглядит только что распечатанным | ревью |
| Текст-заглушка | «Lorem ipsum», «Button1», «New Scene» | поиск по сценам |
| Иконка по умолчанию | стандартный значок движка | `game/icon.svg` заменён |
| Несогласованная палитра | каждый объект своего цвета | наличие палитры в проекте |

**Обязательные следствия:**

- В проекте должна существовать **зафиксированная палитра** (не более 5–7
  основных цветов) и набор материалов, переиспользуемых между объектами.
  Согласованность важнее разнообразия: глаз считывает стиль как
  повторяемость решений, а не как количество уникальных текстур.
- Ни одного имени-заглушки. Узлы, сцены, сигналы и переменные называются по
  смыслу. `Node3D12` в сцене — это дефект, а не временное состояние.
- Масштаб человека — **единица измерения мира**. Высота игрока задана:
  `PLAYER_HEIGHT = 1.8`, `PLAYER_EYE_HEIGHT = 1.62`, `PLAYER_RADIUS = 0.35`.
  Все пропорции в мире отсчитываются от них. Дверной проём ≥ 2.0, ступень
  ≤ 0.25, поручень на 0.9–1.0.
- Освещение сцены — минимум **два** источника с разными ролями (ключевой и
  заполняющий/контровой), плюс окружение. Один `DirectionalLight3D` на всю
  сцену даёт плоскую картинку независимо от качества моделей.

### Требование: стиль

Стиль выбирается исполнителем, но выбирается **один и соблюдается везде**.
Смешение фотореализма и low-poly в одной сцене выглядит как ошибка, даже если
каждая часть выполнена хорошо.

Выбранный стиль записывается в этом документе (раздел дополняется при
принятии решения) и влияет на бюджеты: low-poly допускает больше объектов,
фотореализм — меньше, но с более тяжёлыми материалами.

<a id="2-визуальное-качество"></a>
## 2. Визуальное качество

### 2.1 Рендер

| Параметр | Значение | Причина |
| --- | --- | --- |
| Метод рендеринга | Forward Plus | объявлен в `project.godot` как feature |
| Окружение по умолчанию | `res://resources/environment/default_env.tres` | `background_mode` **не** «чистый цвет» |
| MSAA 3D | 2 по умолчанию, настраивается | меньше — видимые «лесенки» |
| Экранное сглаживание | FXAA по умолчанию | TAA даёт шлейфы на движении |
| TAA | включён в профиле по умолчанию | отключается в настройках |
| Тени направленного света | 4096 | меньше — рваные края на расстоянии |
| Окклюзионное отсечение | включено | экономия на закрытых объектах |
| Масштабирование 3D | режим 1 (FSR) | резерв производительности на слабых машинах |

Проверяется: `tools/lint/godot_scene_check.py`,
`game/tests/smoke/test_scenes_load.gd` (окружение не «чистый цвет»),
`test_game_config.gd`.

### 2.2 Цветокоррекция

Постобработка выполняется одним шейдером `shaders/post_grade.gdshader`.
Профиль качества задаёт тонмаппинг (`tonemap_mode`, `tonemap_white`,
`tonemap_exposure`) и включение коррекции (`adjustment_enabled`).

**Обязательно:** постобработка не подменяет освещение. Если сцена выглядит
приемлемо только после цветокоррекции, проблема в свете и материалах.

### 2.3 Доступность изображения

Шейдер `post_grade.gdshader` содержит параметр `colorblind_mode` со
значениями 0–3 (выключено + три типа дальтонизма). Это не дополнительная
возможность, а часть требования «профессиональный GUI»: 8 % мужчин имеют
ту или иную форму нарушения цветовосприятия, и интерфейс, различимый только
по цвету, для них неработоспособен.

**Правило:** состояние никогда не передаётся цветом alone. Цвет дублируется
формой, положением, подписью или анимацией.

### 2.4 Небо

Небо в меню — процедурный шейдер (`shaders/menu_backdrop_sky.gdshader`),
около 2 КБ.

**HDRI-панорамы запрещены в меню.** Панорама весит 4–20 МБ, грузится при
открытии меню и даёт задержку на первом кадре — то есть именно там, где
игрок формирует первое впечатление. Процедурное небо весит килобайты,
генерируется мгновенно и масштабируется под профиль качества без
перекодирования.

Для игровых сцен HDRI допустимо, если оно проходит конвейер ассетов и
вписывается в бюджет.

<a id="3-3d-модели-и-ассеты"></a>
## 3. 3D-модели и ассеты

### 3.1 Формат

**Единственный формат моделей — glTF 2.0** (`.glb` для бинарного,
`.gltf` для текстового с внешними данными).

Причины, по которым не FBX и не OBJ:

- glTF — открытый стандарт с официальной валидацией (валидатор Khronos
  подключён к конвейеру);
- поддерживает PBR-материалы, скелетную анимацию, сжатие геометрии
  (Draco/meshopt) и сжатие текстур (KTX2/WebP) как часть формата;
- импортируется Godot без промежуточных конвертаций;
- FBX проприетарен, его импорт зависит от версии SDK и регулярно теряет
  материалы и тангенты.

### 3.2 Бюджеты

| Что | Предел | Действие при превышении |
| --- | --- | --- |
| Размер файла модели | 12 МБ | **отказ** принять ассет |
| Рекомендуемый размер | 4 МБ | предупреждение |
| Треугольников в модели | 250 000 | **отказ** |
| Предупреждение | 150 000 | больше половины бюджета |
| Вершин | 200 000 | **отказ** |
| Текстур в одной модели | 32 | **отказ** |
| Сторона текстуры | 4096 px | **отказ** |
| Размер текстуры | 8 МБ | **отказ** |
| Узлов в модели | 512 | предупреждение |
| Размер текстуры в конвейере | 2048 px | пережимается автоматически |

Числа закреплены в двух местах, которые обязаны совпадать:
`game/scripts/util/validators.gd` (`MAX_MODEL_BYTES`, `MAX_TEXTURE_BYTES`) и
`tools/asset-pipeline/scripts/validate_models.mjs`. Соответствие проверяется
тестом `test_validators.gd`.

### 3.3 Обязательная обработка

Каждая модель до попадания в игру проходит конвейер:

```bash
node tools/asset-pipeline/scripts/optimize_models.mjs <каталог> [--ratio=N]
node tools/asset-pipeline/scripts/validate_models.mjs <каталог> --strict
```

Конвейер выполняет: слияние иерархии узлов, удаление дубликатов и неиспользуемых
данных, сварку вершин, упрощение (по запросу), расчёт нормалей и тангент,
пережатие и уменьшение текстур, квантование атрибутов, переупорядочивание
вершин под кэш GPU и сжатие геометрии (meshopt или Draco).

**Тангенты обязательны** для любой модели с картой нормалей. Без них
normal mapping даёт неверное освещение; дефект выглядит как ошибка шейдера,
а причина — в файле модели.

**Нормали обязательны.** Модель без атрибута `NORMAL` не освещается корректно.
Экспортеры из DCC регулярно их теряют, поэтому конвейер считает их сам.

Подробности, включая обоснование порядка операций — в
[`docs/ASSET-PIPELINE.md`](docs/ASSET-PIPELINE.md).

### 3.4 Что валидатор обязан отклонить

Помимо превышения бюджетов:

- **отрицательный масштаб узла** — выворачивает нормали: модель выглядит
  целой, но освещается как вывернутый носок;
- **нулевой масштаб узла** — узел не отрисуется вообще;
- **устаревшее расширение** `KHR_materials_pbrSpecularGlossiness` — Godot 4
  конвертирует его в metallic-roughness с потерями;
- **отсутствие сжатия геометрии** при более чем 1000 треугольников — верный
  признак, что файл не проходил конвейер;
- **оба сжатия одновременно** (Draco и meshopt) — нужно одно;
- **пробелы и не-ASCII в именах узлов** — `get_node()` ищет по точному имени,
  а экспортеры заменяют пробелы или кодируют их; обращение молча возвращает
  `null`;
- **PNG крупнее 1 Мп** — предложение конвертировать в WebP.

### 3.5 Хранение в репозитории

Крупные бинарные файлы хранятся через Git LFS. `.gitattributes` покрывает:
`glb`, `gltf`, `fbx`, `blend`, `ktx`, `psd`, `kra`.

Каталоги:

```
game/assets/models/source/      исходники до оптимизации
game/assets/models/             оптимизированные .glb для игры
game/assets/textures/
game/assets/materials/
game/assets/audio/sfx/
game/assets/audio/music/
game/assets/fonts/
```

**Исходники хранятся вместе с результатом.** Без них повторная оптимизация с
другими параметрами невозможна, а правка ассета превращается в поиск автора.

### 3.6 Процедурное содержимое

Всё, что можно сгенерировать кодом, **генерируется кодом**. В проекте это уже
реализовано для: неба меню, фона главного меню, арены, материалов окружения и
поля ветра.

Это не экономия на качестве, а решение с тремя следствиями:

- нет лицензионных ограничений;
- вес — килобайты вместо мегабайт;
- масштабируется под профиль качества без перекодирования ассетов.

Модели нужны там, где важна уникальная форма: персонажи, предметы, детали
архитектуры. Геометрия, описываемая параметрически (плоскости, колонны,
ящики, terrain), модели не требует.

<a id="4-меню-и-интерфейс"></a>
## 4. Меню и интерфейс

### 4.1 Главное меню

**Требование: трёхмерное меню с игровым содержимым на фоне.**

Реализация: сцена `game/scenes/menu/main_menu.tscn` с фоном
`menu_backdrop.tscn`.

**Корень сцены меню — `Node`, а не `Control`.** Сцена, укоренённая в
`Control`, ненадёжно отображает 3D-содержимое: порядок отрисовки строится
иначе, и 3D-узел оказывается вне ожидаемого места. Внутри `Node` живут
`Node3D`-фон и `CanvasLayer` с интерфейсом.

**Бюджет фона меню** (проверяется `test_menu_backdrop_budget.gd`):

| Параметр | Предел |
| --- | --- |
| Узлов | 512 |
| Треугольников | 500 000 |
| Источников света с тенями | 2 |

Обязательный состав фона: `Camera3D`, `WorldEnvironment` с непустым
`Environment`, процедурное небо, минимум один `DirectionalLight3D`.

**Почему фон меню ограничен жёстче игровой сцены.** Меню открывается первым и
часто — при каждом запуске. Задержка в полсекунды на загрузке фона формирует
впечатление о всей игре. Игровая сцена грузится один раз и через экран
загрузки, где задержка ожидаема.

**Место для пользовательской сцены:** параметр `newwoorld/menu/hero_scene`.
Пустое значение не приводит к ошибке (проверяется тестом), поэтому фон
работает и без неё.

### 4.2 Обязательные экраны

| Экран | Сцена | Требование |
| --- | --- | --- |
| Загрузка | `scenes/boot/boot.tscn` | главная сцена проекта |
| Главное меню | `scenes/menu/main_menu.tscn` | 3D-фон |
| Настройки | `scenes/menu/settings_panel.tscn` | форма строится из схемы |
| Титры и контакты | `scenes/menu/credits_panel.tscn` | **обязательно** |
| Экран загрузки | `scenes/common/loading_screen.tscn` | между сценами |
| Меню паузы | `scenes/common/pause_menu.tscn` | `process_mode = 3` в `.tscn` |

`process_mode = 3` у меню паузы задаётся **в файле сцены**, а не кодом в
`_ready()`: до первого кадра узел уже может получить событие, и меню окажется
замороженным вместе с игрой.

### 4.3 Контакты — обязательное требование

Меню **обязано** содержать контакты. Это требование заказчика, а не
дополнение. Данные берутся из `game/data/credits.json` → `contacts`.

Каждый контакт имеет поля: `id`, `label`, `value`, `kind`, и опционально
`copyable`, `openable`, `note`, `optional`.

Допустимые `kind`: `email`, `url`, `text`, `repo`, `chat`. Значение
проверяется: `url` и `repo` обязаны начинаться с `https://`.

**Обязательно наличие хотя бы одного работающего канала связи.** Проверка
(`test_credits_data.gd`) не пропускает пустой список контактов и контакты без
значений.

**Текущее состояние — заглушки, которые надо заменить:**

| Поле | Сейчас | Действие |
| --- | --- | --- |
| Почта | `hello@example.com` | заменить на настоящую **до релиза** |
| Сайт | `https://example.com` | заменить **до релиза** |
| Сообщество | пусто (`optional: true`) | заполнить или оставить пустым |

Неработающий адрес хуже отсутствующего: правообладатель или игрок, написавший
в никуда, не получит ответа и не узнает, что адрес неверен.

Рабочие сейчас: ссылка на исходный код и на трекер ошибок
(`github.com/standimaoff-oss/NEWwoorld` и `/issues`).

**В Godot нет `LinkLabel`.** Кликабельная ссылка делается либо плоской
`Button` (она же получает фокус, поэтому меню управляемо с клавиатуры и
геймпада), либо `RichTextLabel` с bbcode `[url]` и сигналом `meta_clicked`.

### 4.4 Настройки

Форма настроек **строится из схемы**, а не размечается вручную в сцене.

- Схема: `game/scripts/settings/settings_schema.gd` — 38 ключей в пяти
  разделах: `video` (18), `audio` (6), `input` (4), `gameplay` (6),
  `accessibility` (4).
- Сервис: `game/scripts/autoload/settings_service.gd` — чтение, запись,
  валидация, применение, сохранение на диск.
- Форма: `game/scripts/ui/settings_form.gd` — создаёт виджеты по типу ключа.

Соответствие типа и виджета обязательно: `BOOL` → `CheckBox`, `FLOAT`/`INT` →
`HSlider`, `ENUM` → `OptionButton`, `STRING` → `LineEdit`.

**Добавление настройки = одна запись в схеме.** Править `.tscn` не нужно:
строка появится сама. Это и есть смысл требования «профессиональный GUI,
чтобы его можно было построить без проблем».

Проверяется (`test_settings_form.gd`): число строк равно числу ключей раздела;
класс виджета соответствует типу; значения виджетов равны значениям сервиса;
изменение виджета доходит до сервиса; у каждой строки есть подпись; имя строки
не содержит `/`; **все виджеты получают фокус**; у слайдера не более 21 деления
и `min < max`.

**Все виджеты обязаны быть фокусируемыми.** Меню, недоступное с клавиатуры и
геймпада, не является профессиональным независимо от внешнего вида.

### 4.5 Тема оформления

Тема строится кодом: `game/scripts/ui/theme_builder.gd` (autoload
`ThemeService`). Ручная разметка стилей в каждой сцене запрещена — она
расходится между экранами, и расхождение заметно.

**`Theme.set_stylebox()` принимает объект `StyleBox`, а не строку с именем
типа.** Передача `"Panel"` — типичная ошибка, которая выглядит как «тема не
применяется».

Тема обязана содержать минимум 8 именованных вариаций и размер шрифта подписей
(проверяется смоук-тестом).

### 4.6 Разрешение и масштабирование

Проект рассчитан на 1920×1080 с переопределением для 1280×720. Растяжение:
`canvas_items` / `expand` / `integer`. Интерфейс обязан корректно выглядеть
при любом соотношении сторон от 4:3 до 21:9.

<a id="5-анимация-и-движение"></a>
## 5. Анимация и движение

### 5.1 Требование

Мир **не должен быть статичным**. Статичная сцена воспринимается как
незавершённая независимо от качества моделей: глаз ищет движение, чтобы
определить, «живое» ли пространство.

Заказчик привёл пример — лёгкий ветер. **Это иллюстрация, а не требование.**
Исполнитель свободен выбрать другие приёмы, если они дают тот же результат:
мир меняется во времени без участия игрока.

### 5.2 Обязательные свойства любого фонового движения

| Свойство | Требование | Причина |
| --- | --- | --- |
| Непрерывность | без видимых скачков и петель | цикл «вдох-выдох» читается как сбой |
| Малая амплитуда | движение заметно на периферии, не в центре внимания | иначе отвлекает от игры |
| Дешевизна | не увеличивает число draw call | фоновая анимация не стоит кадров |
| Настраиваемость | отключается в настройках | вестибулярная чувствительность |
| Детерминированность | одинаковый результат на всех платформах | воспроизводимость и отладка |

### 5.3 Реализация ветра в этом проекте

Параметры публикуются как глобальные shader-переменные из
`game/scripts/systems/wind_system.gd`: направление, сила, время, порывы,
турбулентность. Смещение вершин выполняется в `shaders/wind_foliage.gdshader`.

Расчёт шума — в C++ (`gdextension/src/newwoorld_wind_field.cpp`):
целочисленный хеш-шум с трилинейной интерполяцией и фрактальное
суммирование. Намеренно без `float`-хешей и без `sin()`: результат одинаков
на всех платформах.

`WindSystem` — узел в сцене, а не autoload: ветер имеет смысл только внутри
мира, и в меню не нужен.

### 5.4 Ошибка, которую нельзя повторить

**Глобальные shader-параметры сопоставляются по имени.** В языке шейдеров
Godot нет ключевого слова `global`: объявление `uniform float wind_strength;`
в шейдере и публикация параметра `wind_strength` из GDScript связываются
исключительно по совпадению строк. Синтаксически отличить глобальный параметр
от поля материала невозможно.

Следствие: опечатка в имени — это **не ошибка компиляции**, а молча
неработающий эффект. Поэтому имена параметров ветра сверяются статически:
`python3 tools/verify/check_backend_contract.py --strict`.

Исключение, закреплённое в проверке: `wind_response` является uniform-переменной
**материала** (сила отклика конкретного объекта на ветер), а не глобальным
параметром.

### 5.5 Анимация интерфейса

Переходы между экранами и появление элементов — плавные, но **короткие**
(150–300 мс). Длинная анимация меню воспринимается как задержка, а не как
украшение, особенно при повторных открытиях.

Анимация не должна блокировать ввод: нажатие во время перехода либо
обрабатывается, либо отменяет переход.

<a id="6-оптимизация-и-настройки-графики"></a>
## 6. Оптимизация и настройки графики

### 6.1 Профили качества

Четыре профиля: `game/resources/quality/quality_{low,medium,high,ultra}.tres`.

**Бюджеты не убывают от low к ultra** — это проверяется и в
`tools/verify/check_data.py`, и в смоук-тесте. Нарушение порядка означает,
что «низкое» качество оказалось тяжелее «высокого», и игрок, снизивший
настройки, получит худший результат.

Поля профиля (`game/scripts/systems/quality_profile.gd`):

| Группа | Поля |
| --- | --- |
| Идентификация | `profile_id`, `display_name`, `sort_order` |
| Тени | `shadow_map_size`, `shadow_max_distance`, `shadow_split_mode`, `soft_shadow_filter_quality`, `directional_shadows_enabled` |
| Экранное освещение | `ssao_enabled`, `ssil_enabled`, `ssr_enabled`, `sdfgi_enabled`, `glow_enabled`, `volumetric_fog_enabled`, `volumetric_fog_quality` |
| Сглаживание | `msaa_3d`, `screen_space_aa`, `use_taa`, `scaling_3d_mode`, `scaling_3d_scale` (0.5–1.0), `anisotropic_filtering` |
| Геометрия | `mesh_lod_threshold_pixels`, `max_visible_decals`, `destruction_chunk_budget`, `particle_density` (0.05–1.0), `render_distance` |
| Постобработка | `tonemap_mode`, `tonemap_white`, `tonemap_exposure`, `adjustment_enabled` |

Применяет профиль `QualityService` (autoload): находит окружение в группе
`world_environment` и солнце в группе `main_sun`, применяет параметры.

**Группы обязательны.** Профиль, применяемый через обход дерева и поиск по
имени узла, сломается при переименовании. Группы (`&"world_environment"`,
`&"main_sun"`) — контракт между сценой и сервисом.

### 6.2 Производительность

| Правило | Требование |
| --- | --- |
| Объекты, создающиеся и удаляющиеся часто | **только через пул** (`systems/object_pool.gd`) |
| Метрики кадра | собирает `PerfMonitor`: FPS, среднее, p95, худший кадр, время `process`/`physics`, память, draw calls, примитивы, число узлов, тела физики, пары столкновений, рывки |
| Оверлей отладки | читает снимок метрик; по умолчанию **выключен** |
| Журнал событий | кольцевой (`Diagnostics`): уровень, тег, сообщение, время, кадр |

**Обломки разрушения — главный потребитель пула.** Они создаются и удаляются
сотнями. Без пула это сотни аллокаций на кадр и рывки именно в момент взрыва,
то есть тогда, когда просадка заметнее всего.

### 6.3 Ключи снимка метрик

Оверлей читает из снимка `PerfMonitor.build_snapshot()` ровно эти ключи:

```
fps, avg_frame_ms, p95_frame_ms, worst_frame_ms, process_ms, physics_ms,
static_mem_mb, peak_mem_mb, video_mem_mb, draw_calls, primitives, nodes,
objects, resources, physics_bodies, collision_pairs, hitches
```

Ключи вынесены в константы `K_*` и список `SNAPSHOT_KEYS`, а соответствие
проверяется `test_debug_overlay_contract.gd`.

**Почему это требование, а не деталь реализации.** Линтеры **не проверяют
ключи словарей**: `snapshot.get("wrong_key")` возвращает `null` без ошибки.
В проекте уже случился случай, когда оверлей читал 10 несуществующих ключей —
синтаксис верный, типы верные, а интерфейс молча показывал пустоту. Найти это
по коду невозможно; находится только сверкой источника и потребителя.

### 6.4 Что не измеряется автоматически

Замеров времени на реальном железе в проекте нет сознательно: на CI раннер
каждый раз разный, и порог «не медленнее 16 мс» давал бы случайные провалы
без изменений в коде. Вместо замеров используются **бюджеты** — числа, которые
можно проверить статически.

Профилирование выполняется человеком через оверлей отладки на целевой машине.

<a id="7-физика-и-разрушение"></a>
## 7. Физика и разрушение

### 7.1 Параметры физики

| Параметр | Значение |
| --- | --- |
| Частота шага | 60 Гц (проверяется: допустимо 30–120) |
| Гравитация | 9.81 м/с² |
| Слоёв физики | 8, имена заданы в `project.godot` |
| Слоёв рендера | 5: `Default`, `FirstPerson`, `Ghost`, `Outline`, `Fx` |

Слои физики: `World`, `Player`, `Enemy`, `Projectile`, `Interactable`,
`Debris`, `Trigger`, `Ragdoll`.

**Обязательные свойства масок** (проверяются `test_game_config.gd`):

- слои идут подряд от 1 до N и не превышают 32;
- маска игрока **включает** `World` и `Interactable`;
- маска игрока **исключает** `Player` — иначе персонажи сталкиваются друг с
  другом и выталкивают себя из геометрии;
- `INTERACT_MAX_DISTANCE` (3.0) больше `PLAYER_RADIUS` (0.35) — иначе
  взаимодействие невозможно в упор.

### 7.2 Разрушение

Параметры в `GameConfig`:

| Константа | Значение | Смысл |
| --- | --- | --- |
| `DESTRUCTION_MAX_ACTIVE_CHUNKS` | 1024 | жёсткий потолок обломков в мире |
| `DESTRUCTION_MAX_CONCURRENT_BREAKS` | 4 | сколько объектов ломается одновременно |
| `DESTRUCTION_DEBRIS_LIFETIME` | 12.0 с | время жизни обломка |
| `DESTRUCTION_CELL_SIZE` | 0.5 м | шаг воксельной сетки разбиения |

Сервис: `game/scripts/systems/destruction_service.gd`.
Минимальная энергия разрушения: `MIN_BREAK_ENERGY = 12.0`.

### 7.3 Два бэкенда — обязательное требование

Разрушение работает через **C++** (`NewwoorldFracturer`) с автоматическим
переключением на **GDScript**, если расширение не собрано или не загрузилось.
Выбор — через `ClassDB.class_exists()`.

**Требование: игра запускается и работает без собранного расширения.**

Причина не в удобстве. Нативное расширение собирается под каждую платформу
отдельно, и на машине игрока его может не оказаться (или оно не загрузится).
Игра, падающая в таком случае, неработоспособна; игра, переключившаяся на
запасной путь, просто медленнее.

### 7.4 Контракт бэкендов — критическое требование

Оба бэкенда обязаны возвращать данные **одинаковой формы**. Каждый обломок —
словарь с ключами:

```
mesh, offset, impulse, spin, piece_index, voxel
```

Ключи перечислены в `DestructionService.PIECE_KEYS` и сверяются статически:
```bash
python3 tools/verify/check_backend_contract.py --strict
```

**Это требование появилось из реальной ошибки.** C++-бэкенд возвращал ключ
`voxel`, GDScript — нет. Оба работали по отдельности, а поведение игры
зависело от того, загрузилось расширение или нет. Ошибка неотличима от
«случайных глюков», и ищется в физике, а не в форме данных.

### 7.5 Как работает разбиение

`NewwoorldFracturer.fracture(mesh, transform, impact_point, impact_normal,
energy, cell_size, chunk_budget)` → массив словарей-обломков.

Три решения, каждое со своей причиной:

**Обломки сортируются по расстоянию до точки удара, а бюджет отбрасывает
ДАЛЬНИЕ.** Интуитивно хочется отбросить ближние — они мельче. Но при взрыве
игрок смотрит на точку удара: потеря дальнего обломка незаметна, потеря
ближнего выглядит как «взрыв не сработал».

**Вращение детерминировано** (хеш от индекса и координат ячейки). Случайное
вращение сделало бы повтор одного взрыва визуально разным, что ломает и
воспроизводимость тестов, и ощущение контроля.

**Вершины переназначаются на каждый обломок.** Общий буфер означал бы, что GPU
обрабатывает вершины всех обломков, включая невидимые.

Жёсткий потолок в C++ — `kHardChunkCap = 512`: один вызов не может породить
тысячи тел.

### 7.6 Ошибки физики, которые нельзя повторить

| Ошибка | Правильно |
| --- | --- |
| `Area3D` не обнаруживается лучом | у цели `monitorable = true` |
| Луч попадает в `CollisionShape3D`, а логика в родителе | подниматься по родителям до узла с методом или группой |
| Смена слоя физики в физическом колбэке игнорируется | `set_deferred()` |
| `is_on_floor()` пропадает на кадре на склоне | небольшое отрицательное `velocity.y` на полу |
| `MeshDataTool.create_from_surface(mesh)` | нужен `ArrayMesh`; для примитивов — `SurfaceTool.create_from()` → `commit()` |
| Число треугольников `BoxMesh` равно нулю | у примитивов **пустой** `ARRAY_INDEX`; считать по `ARRAY_VERTEX` |
| `CollisionObject3D.PROCESS_MODE_DISABLED` | константы процесса — у `Node`, не у `CollisionObject3D` |

### 7.7 Взаимодействие

`game/scripts/world/interactable.gd`. Ограничения:
`INTERACT_MAX_DISTANCE = 3.0`, `INTERACT_MAX_ANGLE_DEG = 45.0`.

Угол обязателен: без него игрок взаимодействует с объектом за спиной, и
подсказка «нажмите E» появляется на том, что не видно.

Обводка доступного объекта выполняется через `material_overlay`, а не
`material_override`: последний заменяет материал целиком, и объект теряет
собственную текстуру.

<a id="8-сторонние-ассеты-и-лицензии"></a>
## 8. Сторонние ассеты и лицензии

### 8.1 Требование заказчика

> Для моделей, которые ИИ сложно сделать (например, человек), можно брать
> ассеты со свободных форумов — только действительно свободные, либо с
> указанием авторства.

Это требование реализуется **двумя файлами, которые обязаны быть
согласованы**:

- `game/data/credits.json` → `used_assets` — машинно проверяемый перечень;
- `game/assets/ATTRIBUTION.md` — документ, который читает человек.

Согласованность проверяется тестом `test_credits_data.gd` и заданием CI
`assets`: имя каждого ассета из JSON обязано встречаться в Markdown, и у
каждого обязана быть лицензия.

### 8.2 Разрешённые лицензии

| Лицензия | Атрибуция |
| --- | --- |
| CC0 1.0 Universal | не требуется — **предпочтительный выбор** |
| MIT, Apache-2.0, BSD-2/3-Clause, Zlib, ISC | требуется |
| CC-BY 3.0/4.0 | требуется |
| CC-BY-SA 3.0/4.0 | требуется; **заразная** — производная работа идёт под той же лицензией |
| OFL 1.1 | только шрифты |

Список хранится в `game/scripts/util/validators.gd` и **оттуда же читается**
проверкой данных. Дублировать его в другом месте запрещено: раньше он был
скопирован в `check_data.py` с комментарием «совпадают», и комментарий врал —
сверки не существовало, поэтому добавление лицензии в GDScript не меняло
поведение проверки.

### 8.3 Запрещённые лицензии

| Лицензия | Почему нельзя |
| --- | --- |
| CC-BY-NC и производные | запрет коммерческого использования; игра с любой монетизацией — нарушение |
| CC-BY-ND | запрет производных работ, а **оптимизация конвейером — уже производная работа** (упрощение, пережатие текстур) |
| Проприетарная, включая Mixamo | бесплатно ≠ свободно; условия Adobe запрещают перераспространение |
| «Royalty free» без текста лицензии | маркетинговая формулировка, а не лицензия |
| Любая custom EULA без явного разрешения перераспространения | условия нельзя проверить, значит нельзя и соблюдать |

Последний пункт — самая частая ошибка. «Бесплатно для использования» и
«разрешено распространять в составе продукта» — разные права, и второе
требуется для любой игры, которую скачивают.

### 8.4 Одобренные источники

| Источник | Лицензия | Условие |
| --- | --- | --- |
| Kenney | CC0 | атрибуция не требуется, но приветствуется |
| Poly Haven | CC0 | HDRI, текстуры, модели |
| ambientCG | CC0 | PBR-материалы |
| Quaternius | CC0 | low-poly пакеты, включая персонажей |
| KayKit | CC0 (проверять по пакету) | часть пакетов CC0; лицензию смотреть на странице пакета |
| OpenGameArt | разные | **читать лицензию каждого файла** — там есть и CC0, и CC-BY-NC |
| Sketchfab | разные | фильтр по CC0 безопасен; CC-BY требует атрибуции |
| Mixamo | проприетарная | **не использовать для перераспространения** |

KayKit и Quaternius — практичный выбор именно для персонажей, то есть для
того случая, который заказчик назвал трудным для самостоятельного создания.

### 8.5 Обязательные поля записи об ассете

```json
{
  "name": "…",
  "author": "…",
  "license": "CC0",
  "url": "https://…",
  "kind": "model | texture | audio | font | tooling | engine",
  "attribution_required": false
}
```

**Если `attribution_required` равно `true`, автор обязан быть указан.**
Проверка не пропускает запись с флагом и без автора: «требуется атрибуция, но
неизвестно кому» — невыполнимое обязательство.

Для CC-BY уведомление обязано содержать все четыре элемента: имя автора,
название работы, ссылку на источник, ссылку на текст лицензии — **плюс
отметку о внесении изменений**. Пропуск любого элемента — нарушение лицензии,
даже если файл «бесплатный».

### 8.6 Текущее состояние

**Сторонних игровых ассетов в проекте нет.** Всё визуальное содержимое
создаётся процедурно (см. [3.6](#36-процедурное-содержимое)).

В `used_assets` записаны девять инструментов и библиотек, попадающих в
репозиторий или связываемых со сборкой: Godot Engine, GUT, godot-cpp,
gdtoolkit, glTF-Transform, Draco, meshoptimizer, sharp, mikktspace. Все с
указанием автора, лицензии и источника.

### 9.1 Языки

| Язык | Где | Почему |

(`godot-cpp`). Расширение компилируется в разделяемую библиотеку и
подключается файлом `game/bin/newwoorld.gdextension` — **пересборка движка не
требуется**. Подробности в [`docs/CPP-EXTENSION.md`](docs/CPP-EXTENSION.md).

C++ применяется **только** там, где GDScript не справляется: массовые
вычисления на кадр (поле ветра для сотен объектов) и геометрия (разбиение
меша на сотни обломков). Всё остальное — на GDScript: он быстрее
разрабатывается, не требует сборки под каждую платформу и не создаёт риска
молчаливой незагрузки.

### 9.2 Слои

```
игра        game/scenes/game/     мир, игрок, HUD
меню        game/scenes/menu/     главное меню, настройки, титры
каркас      game/scripts/         сервисы, системы, утилиты
нативный    gdextension/src/      C++
```

**Зависимости идут только вниз.** Каркас не знает о существовании меню.
Нативный слой не знает о каркасе.

Нарушение направления — самый дорогой вид ошибки в проекте: он не ловится
компилятором и приводит к циклам инициализации autoload, которые проявляются
как случайные `null` в рантайме.

### 9.3 Константы — в одном месте

Все числа, общие для нескольких мест, объявлены в `GameConfig` (первый
autoload). Дублирование константы в двух файлах — defect: рано или поздно
одно место правят, а второе нет.

### 9.4 `project.godot` генерируется

Файл создаётся `tools/setup/generate_project_godot.py` и **не редактируется
руками**. Причина: сериализация `Object(InputEventKey, …)` многословна и
строга, а редактор Godot пересохраняет файл по-своему, создавая шумный diff.

Ручная правка не ломает игру сразу — она молча расходится с генератором и
стирается при следующей генерации. Проверка расхождения:

```bash
python3 tools/setup/generate_project_godot.py --check
```

Содержимое: 11 autoload, 30 действий ввода (клавиатура/мышь **и** геймпад),
разрешения и растяжение, параметры физики и рендера, имена слоёв.

**Порядок autoload значим:** сервис может обращаться в `_ready()` только к
загруженным раньше него. `GameConfig` идёт первым, потому что не зависит ни от
чего и нужен всем.

### 9.5 Стиль

Конфигурация в `.gdlintrc` и `.editorconfig`:

| Правило | Значение |
| --- | --- |
| Отступы | **табы** |
| Длина строки | 100 |
| Длина файла | 700 строк |
| Аргументов функции | 8 |
| Локальных переменных | 40 |
| `return` в функции | 6 |
| Публичных методов | 22 (в тестах — 80) |

**Лимиты не поднимаются — код разделяется.** В проекте это случилось один раз:
`settings_service.gd` (876 строк) разделён на сервис и
`settings/settings_schema.gd`. Разделение оказалось содержательным: схема —
чистые данные, и форма интерфейса строится по ней без участия сервиса.

Порядок объявлений в файле проверяется строго: `tools`, `classnames`,
`extends`, `docstrings`, `signals`, `enums`, `consts`, `staticvars`,
`exports`, `pubvars`, `prvvars`, `onreadypubvars`, `onreadyprvvars`, `others`.
`const` после `func` — ошибка.

### 9.6 Комментарии

**Каждый комментарий объясняет ПОЧЕМУ, а не ЧТО.** Код сообщает, что
происходит; комментарий нужен там, где без него читатель сделает неверный
вывод или «исправит» работающее.

Наиболее ценны комментарии, зафиксировавшие реальную ошибку: они
предотвращают её повторение. В проекте такие комментарии обязательны в
проверках и в конвейере ассетов.

Язык комментариев — русский, единообразно во всём репозитории.

<a id="10-проверка-и-приёмка"></a>
## 10. Проверка и приёмка

### 10.1 Одна команда

```bash
bash tools/verify/verify_all.sh --strict
```

Выполняет всё, что доступно в текущей среде. То же самое выполняет CI — теми
же командами. Это осознанное дублирование: если локально зелёное, а в CI
красное, расхождение между ними само по себе является дефектом.

Через `make`: `make check`, `make verify`, `make strict`, `make quick`,
`make test`, `make help`.

### 10.2 Что проверяется

| Шаг | Инструмент | Что ловит |
| --- | --- | --- |
| GDScript: синтаксис | `gdparse` | код не загрузится |
| GDScript: формат | `gdformat` | расхождение стиля |
| GDScript: стиль | `gdlint` | лимиты, порядок объявлений |
| GDScript: API | `godot_api_check.py` | несуществующие методы, свойства, константы |
| GDScript: вызовы | `gdscript_call_check.py` | неверное число и типы аргументов |
| Сцены и ресурсы | `godot_scene_check.py --strict` | `load_steps`, висячие ссылки |
| Шейдеры | `shader_check.py` | синтаксис, необъявленные uniform |
| Контракт бэкендов | `check_backend_contract.py --strict` | расхождение C++ и GDScript |
| Данные | `check_data.py` | JSON, схема настроек, `project.godot`, профили |
| Гигиена репозитория | `check_repo_hygiene.py` | мусор в git, обязательные файлы, права |
| Ассет-конвейер | `check_pipeline.mjs` | 24 проверки работоспособности |
| C++ | `cpp/syntax_check.sh --objects` | ошибки компиляции |
| Тесты GUT | Godot + GUT | 11 файлов, все категории |

### 10.3 Три исхода, а не два

| Состояние | Код | Смысл |
| --- | --- | --- |
| ПРОЙДЕНО | 0 | проверено, нарушений нет |
| ПРОВАЛ | 1…124 | проверено, найдены нарушения |
| **ПРОПУЩЕНО** | **125** | инструмент недоступен |

Разделение обязательно. Если «инструмент не установлен» считать провалом —
прогон вечно красный, и его перестают читать. Если считать успехом —
пропускаются настоящие ошибки, и доверие к зелёному результату пропадает.

Итоговый отчёт печатает пропуски отдельной строкой и добавляет:
**«пропущено N — это НЕ «всё хорошо»»**.

### 10.4 Категории тестов

| Каталог | Вопрос | Файлов |
| --- | --- | --- |
| `unit/` | правильна ли логика | 9 |
| `integration/` | работают ли части вместе | 1 |
| `smoke/` | загружается ли вообще | 1 |

Подробности — в [`docs/TESTING.md`](docs/TESTING.md).

**Каждый тестовый файл начинается с комментария о том, какой класс ошибок он
ловит.** Тест без внятного ответа на «зачем» проверяет реализацию, а не
поведение, и ломается при любом рефакторинге.

### 10.5 Ограничения среды

**В среде разработки невозможно:** запустить игру, выполнить тесты GUT,
экспортировать сборку, слинковать расширение целиком, собрать через CMake,
скросс-компилировать под Windows. Причина — отсутствие бинарника Godot,
`cmake` и `mingw`, а также загрузка файлов релизов GitHub заблокирована.

**Всё перечисленное выполняется в CI** (`.github/workflows/godot-ci.yml`):
задания `lint`, `cpp-syntax`, `tests`, `build-extension` (4 платформы),
`cmake-smoke`, `assets`, `godot-latest`.

Локально выполняется вся статическая проверка — и её достаточно, чтобы не
пустить в CI заведомо сломанный код.

<a id="11-критерии-готовности"></a>
## 11. Критерии готовности

Задача считается выполненной, когда выполнены **все** пункты.

### Код

- [ ] `bash tools/verify/verify_all.sh --strict` — 0 провалов
- [ ] Пропусков нет, либо каждый объяснён отсутствием инструмента
- [ ] CI зелёный, включая задания `tests` и `build-extension`
- [ ] Тестов выполнено больше сотни; в логе GUT нет `Failing` с ненулевым
      числом
- [ ] Запуск `boot.tscn` не даёт `SCRIPT ERROR`, `Parse Error`,
      `Cannot instantiate`

### Игра

- [ ] Игра запускается и доходит до главного меню
- [ ] Из меню достижимы: настройки, титры с контактами, игровой уровень, выход
- [ ] Меню управляемо **и** мышью, **и** клавиатурой, **и** геймпадом
- [ ] Все четыре профиля качества применяются без ошибок
- [ ] Настройки сохраняются между запусками
- [ ] Меню паузы работает и не замораживается вместе с игрой

### Качество изображения

- [ ] Фон меню в бюджете: ≤512 узлов, ≤500 000 треугольников, ≤2 теневых
      источника
- [ ] Небо меню процедурное, не HDRI
- [ ] Ни одного имени-заглушки в сценах (`Node3D12`, `Button1`, `New Scene`)
- [ ] Ни одного текста-заглушки
- [ ] Иконка приложения заменена со стандартной
- [ ] Палитра зафиксирована и соблюдается

### Ассеты

- [ ] Каждая модель прошла конвейер и валидацию `--strict`
- [ ] Каждый сторонний ассет записан в **оба** файла: `credits.json` и
      `ATTRIBUTION.md`
- [ ] Ни одного ассета под запрещённой лицензией
- [ ] У каждой записи с `attribution_required: true` указан автор

### Контакты и правообладатели

- [ ] `hello@example.com` и `https://example.com` заменены на настоящие
- [ ] Хотя бы один канал связи действительно работает (проверить отправкой)

### Документация

- [ ] `README.md` описывает установку, запуск и проверку
- [ ] `docs/` покрывает архитектуру, тестирование, проверки, конвейер,
      C++ и решения проблем
- [ ] `game/assets/ATTRIBUTION.md` актуален
- [ ] `LICENSE` на месте

<a id="12-запрещено"></a>
## 12. Запрещено

Каждый пункт — за реальной ошибкой или за риском, который невозможно
обнаружить позже.

### В коде

1. **Не поднимать лимиты линтера вместо исправления кода.** Лимит — это
   сигнал, что функция или файл делают слишком много.
2. **Не дублировать константы.** Одно число — одно место (`GameConfig`).
3. **Не редактировать `project.godot` руками.** Только генератор.
4. **Не полагаться на проверку ключей словаря линтером.** Её не существует.
   Ключи — в константы у источника данных, соответствие — в контрактный тест.
5. **Не делать autoload из того, что нужно только одной сцене.** `WindSystem` —
   узел в сцене, потому что в меню ветер не нужен.
6. **Не обращаться к autoload, загруженному позже.** Порядок значим.
7. **Не оставлять состояние изменённым после теста.** Autoload живёт весь
   прогон; невосстановленное состояние ломает следующие тесты, и падают они,
   а не виновник.

### В движке

8. **Не использовать `Engine.has_singleton()` для autoload.** Это разные
   механизмы.
9. **Не ставить `process_mode` меню паузы кодом в `_ready()`.** Только в
   `.tscn`.
10. **Не укоренять сцену с 3D-фоном в `Control`.** Только `Node`.
11. **Не отключать RTTI при сборке расширения.** `cast_to<T>()` использует
    `dynamic_cast`; с `-fno-rtti` код компилируется и врёт в рантайме.
12. **Не собирать расширение против версии новее `compatibility_minimum`.**
    ABI обратно совместимо в одну сторону.
13. **Не менять слои физики без `set_deferred()` внутри физического колбэка.**

### В ассетах

14. **Не класть в игру модель, не прошедшую валидатор.** Бюджеты — не
    рекомендация.
15. **Не использовать ассет без записи в обоих файлах атрибуции.**
16. **Не брать ассеты под NC и ND-лицензиями.** Оптимизация конвейером — уже
    производная работа.
17. **Не брать «royalty free» без текста лицензии.**
18. **Не использовать Mixamo-контент для перераспространения.**
19. **Не хранить исходники моделей вне репозитория.** Без них повторная
    оптимизация невозможна.

### В интерфейсе

20. **Не передавать состояние только цветом.** Обязательно дублирование
    формой, положением или подписью.
21. **Не делать нефокусируемые элементы управления.** Меню обязано работать с
    клавиатуры и геймпада.
22. **Не размечать стили в каждой сцене отдельно.** Только тема из
    `ThemeService`.
23. **Не оставлять неработающие контакты.** Хуже отсутствующих: написавший в
    никуда не узнает, что адрес неверен.

### В процессе

24. **Не считать пропущенную проверку пройденной.** «Пропущено 3» ≠ «всё
    хорошо».
25. **Не чинить проверку вместо кода, который она поймала.** Проверка
    сообщает о дефекте; «починка» проверки скрывает его.
26. **Не вводить два источника истины.** Если список нужен в двух языках,
    один читается из другого — как списки лицензий читаются из
    `validators.gd`.
27. **Не использовать `str.replace()` в патч-скриптах без `assert`.** Метод
    молча ничего не делает, если якорь не найден: получается «правка
    применена» при неизменном файле.
